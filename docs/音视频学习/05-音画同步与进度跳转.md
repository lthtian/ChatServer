# 第五阶段：Qt 音频输出、音画同步与进度跳转

## 1. 解码与播放之间还隔着什么

```text
一个 AVFormatContext 顺序读包
    ├─ 视频 AVCodecContext → AVFrame → SwsContext → RGB QImage
    │                                              ↓
    │                                等待显示时机 → VideoView
    └─ 音频 AVCodecContext → AVFrame → SwrContext → S16 交错 PCM
                                                   ↓
                            应用缓冲 → QAudioOutput → 系统/设备
```

FFmpeg 负责得到图像和声音数值，不负责本程序的播放按钮、声卡输出或显示时机。Qt 音频 API 接收的是解码后的 PCM，不是 AAC 包或 MP4 文件。

三个进度必须分开：已经解码的数据、已经提交给设备的数据、设备已经消费的数据。提前解码和提前写入缓冲可以防止断音，但画面不能跟着“已提交量”提前显示。

## 2. 模块、对象与线程

| 模块 | 保存什么、负责什么 | 不负责什么 |
|---|---|---|
| `MediaDecoder` | 容器、两个解码实例、像素转换器、重采样器；读包、转换、定位 | 控件与声音设备 |
| `AudioOutput` | Qt 音频设备、目标格式、PCM 缓冲、已提交量；输出及消费位置估计 | AAC 解码和视频显示 |
| `MediaWindow` | 播放状态、会话编号、待显示图像、时钟与控件 | 执行耗时的 FFmpeg 解码 |
| `VideoView` | 当前拥有像素的 QImage，等比例绘制 | 决定何时切换画面 |
| `ProgressSlider` | 鼠标位置到进度值的映射 | 执行 FFmpeg seek |

MediaDecoder 在 QThread 工作线程中运行。MediaWindow、AudioOutput 和 QWidget 都在 GUI 线程中使用。跨线程信号通过排队连接传递，GUI 不直接操作解码上下文。音频设备与它返回的 QIODevice 也不在两个线程间交替调用。

跨线程结果为 `MediaBatch`：若干 `VideoPicture`、若干 `AudioBlock` 和 eof 标记。QImage 与 QByteArray 持有自己的数据；工作线程随后 unref AVFrame，不会破坏 GUI 缓冲。`Q_DECLARE_METATYPE` 声明自定义类型，`qRegisterMetaType` 使排队信号能保存并传递它。

这里一次 Read 对应一次读包，而不是一张画面：音视频包交错出现，一个包也可能暂时没有解码输出。GUI 最多保留一个在途读取请求，并根据声画准备量决定是否继续请求。

## 3. Qt 5 的音频对象分别是什么

### QAudioDeviceInfo：设备描述

它描述设备能力，不保存待播放 PCM。`defaultOutputDevice()` 返回系统默认输出设备的描述；`availableDevices(QAudio::AudioOutput)` 列出可用输出设备。

`isNull()` 不足以覆盖所有后端的无设备情况：本机 Qt 5 Windows 后端在没有实际设备时仍可能给出默认设备描述。还需检查设备列表及最终打开结果。

| API | 参数与结果 | 本例用途 |
|---|---|---|
| `availableDevices(mode)` | mode 为 AudioOutput 或 AudioInput；返回设备描述列表 | 确认存在输出设备 |
| `defaultOutputDevice()` | 返回默认输出设备描述 | 选择本播放器的输出设备 |
| `isFormatSupported(format)` | 输入完整 QAudioFormat，返回是否支持该组合 | 在实际创建输出前检查格式 |
| `supportedSampleRates()` | 返回支持的采样率候选列表，单位 Hz | 48 kHz、44.1 kHz 不支持时继续选择 |
| `preferredFormat()` | 返回后端给出的优选描述 | 可辅助诊断，不能替代实际打开验证 |
| `deviceName()` | 返回设备名称 | 显示协商结果 |

单独支持某个采样率和某个位深，不代表它们与任意声道数的组合都可用，因此最终检查完整 format。

### QAudioFormat：PCM 字节的解释规则

它是一个格式描述值，不持有声音数据，也不执行重采样。

```cpp
format.setCodec("audio/pcm");
format.setSampleRate(48000);
format.setChannelCount(2);
format.setSampleSize(16);
format.setSampleType(QAudioFormat::SignedInt);
format.setByteOrder(QAudioFormat::LittleEndian);
```

| 设置 | 含义 | 必须区分的概念 |
|---|---|---|
| `setCodec("audio/pcm")` | 交给设备的是 PCM | 不是源文件的 AAC 编码 |
| `setSampleRate(rate)` | 每声道每秒的采样数量 | 不是音高，也不是码率 |
| `setChannelCount(2)` | 一个时刻有两个声道采样 | 本例重采样目标明确为 stereo |
| `setSampleSize(16)` | 一个声道的一个采样占 16 位 | 是 bit，不是 byte |
| `setSampleType(SignedInt)` | 按有符号整数解释位模式 | 16 位宽与整数类型共同确定 S16 |
| `setByteOrder(LittleEndian)` | 多字节数值低字节在前 | 不表示左右声道排列顺序 |

Qt 此输出路径接收声道交错 PCM。上述格式的一组同时刻采样是 `L R`，占 `2 × 2 = 4` 字节；48 kHz 每秒占 192000 字节。SwrContext 的输出采样率必须与实际选中的 Qt 格式一致；仅修改 QAudioFormat 不会转换数据。

| 换算 API | 含义 |
|---|---|
| `bytesPerFrame()` | 一组同时刻的所有声道采样共占多少字节，本例为 4 |
| `bytesForDuration(us)` | 某段时长需要的字节量，输入单位为微秒 |
| `durationForBytes(bytes)` | 这些字节对应的时长，返回微秒 |

这里的 frame 指“一组同时刻的声道采样”，不是 FFmpeg 的 AVFrame。一个音频 AVFrame 通常包含很多组这样的采样。

本例只在设备支持的 S16、stereo、小端组合中选择采样率；不支持时明确报错，不把其他格式的数据冒充 S16。

### QAudioOutput：正在输出声音的实例

`QAudioOutput(device, format)` 按指定设备和格式创建工作对象。它不同于设备描述，也不自动识别传入数据的格式。

| API | 作用、参数及注意点 |
|---|---|
| `setBufferSize(bytes)` | 请求设备缓冲大小，单位字节，须在 start 前设置 |
| `start()` | 启动推送模式，返回已经打开的可写 QIODevice 指针 |
| `start(QIODevice*)` | 另一种拉取模式，由 Qt 从调用者提供的可读设备取 PCM；本例不用 |
| `bufferSize()` | 查询实际缓冲大小，可能与请求值不同 |
| `periodSize()` | 每个设备处理周期建议提供的字节量 |
| `bytesFree()` | 当前可接受的空闲字节量；不能当作已经播放的字节总数 |
| `suspend()` | 暂停声音处理，保留缓冲供继续播放 |
| `resume()` | 从暂停状态恢复 |
| `reset()` | 立即丢弃缓冲数据；seek、切文件时使用 |
| `stop()` | 停止输出并释放相关系统资源，不能替代暂停保存状态 |
| `setVolume(value)` | 本输出实例的线性音量，0 为静音，1 为满音量 |
| `state()` / `error()` | 查询设备状态与错误原因 |
| `stateChanged(state)` | 状态变化信号，可用于响应设备异常；本例在 Tick 写入时检查状态 |

`start()` 返回的 QIODevice 属于 QAudioOutput，只借用，不自行 delete。停止、reset 或重新 start 后，旧指针不再用于写入；本例重新取得 sink_。

Qt 5 的 QAudioOutput 在这里负责 PCM 输出。阅读其他版本资料时要核对类的职责，不能直接照搬 Qt 6 的音频输出类组合。

## 4. PCM 怎样真正交到设备

```text
协商 QAudioFormat → 创建 QAudioOutput → setBufferSize → start()
                                                       ↓
                                              得到 QIODevice* sink
                                                       ↓
AudioBlock → 应用缓冲 → 组成一个设备周期 → sink->write(data, bytes)
                                                       ↓
                                              保留未接受的剩余字节
```

`QIODevice::write(const char* data, qint64 bytes)` 接收字节地址与请求长度，返回实际接受的字节数；可能少于请求量，返回 -1 表示错误。它不返回采样数或播放时长。返回 0 时本轮停止写入，等后续 Tick 再尝试，不能忙等。

本例先准备一个 periodSize 大小的块，在 bytesFree 足够时提交。按实际返回值减少待写字节并增加 written_bytes_，未接受的部分仍由 period_ 保存。最后不足一个周期时补静音提交，但媒体结束位置不包括补零。

### PCM 的时间信息、静音与数据间隙

音频 AVFrame 同样有起始 PTS，一帧内部的采样按固定时间间隔排列。将起始 PTS 换算为秒，记为 t0，则第 n 个采样对应 `t0 + n / sample_rate`，整帧覆盖的时长为 `nb_samples / sample_rate`；采样数均按每个声道计算。例如从 1 秒开始、48 kHz、每声道 4800 个采样的一块数据，覆盖 `[1.0 秒，1.1 秒)`。

裸 PCM 数组只存采样值，时间信息由 AVFrame 或本例的 AudioBlock 等结构携带。`sink_->write(pcm_data, byte_count)` 没有 PTS 参数：设备按配置的采样率顺序消费字节，播放器需要在提交前处理好时间关系。

AudioBlock 同时保存 PCM 字节与媒体 PTS。AudioOutput 把 PTS 换算成相对于本次输出起点的采样位置：

- 块的起点晚于下一次应写位置：按需补静音，保留音轨起始偏移。
- 块的起点早于下一次应写位置：裁去重叠采样。
- 正好接上：连续写入。

时间间隙按周期逐段填充，不为一段很长的静音一次分配巨大数组。静音的数值与样本格式有关；本例 S16 的静音为全零。

“静音段”和“没有音频数据的时间段”不同：前者仍有占据播放时间的采样；后者需要播放器根据时间戳识别，再决定补静音或处理时间跳变。补静音通常是生成对应数量的 PCM 零值，不要求创建特殊的“静音帧”。音轨可以晚于视频开始、早于视频结束，并不保证覆盖整个视频时段；也不能假定解码器自动补齐所有间隙。

本例保留并补齐音轨起始间隙，之后按连续累计采样定位；流中途任意时间戳跳变尚未完整支持。设备因供给不足而断音，与播放器依据媒体时间戳有意补入静音，是两种情况。

### 音量与静音

`setVolume` 使用线性比例，而人的响度感受不是线性的。滑块值先通过 `QAudio::convertVolume(value, LogarithmicVolumeScale, LinearVolumeScale)` 转换，再提交。静音只将输出设为零，保留用户的音量值；取消静音后恢复它。

## 5. 音频时钟与视频显示

### 公共时间轴

视频 PTS、音频 PTS 各自先从流时间基换成微秒，再减去同一个容器起点。不能把两条轨道分别以自己的首帧归零，否则原本存在的声画偏移会被消除。

Sintel 样本中，视频从零开始，首个实际解码音频帧位于约 0.021333 秒。音频前面留出约 21.33ms 静音后才输出该帧，维持容器描述的关系。

重采样后的 PCM 用“起始时间 + 累计输出采样数 / 输出采样率”定位。累计总数后再换算，避免每一块时长分别舍入再相加导致漂移；重采样器暂未交出的采样不提前计入输出量。

### 为什么选择音频为主时钟

共同时间零点负责对齐各轨道的位置，主时钟负责回答“此刻播到哪里”。主时钟不由哪条流更长决定；音视频可能等长，也可能任意一方先结束。视频帧 PTS 标记应该显示的时刻，本身不会随现实时间前进；最后解码出的 PTS 也不等于当前播放位置。

音频设备按采样率连续消费 PCM。为了追随画面而随意暂停供给、删除或重复采样，可能造成断音、爆音或听得出的变化。视频则可以延长一张画面的显示，或跳过已经迟到的待显示图像。因此，本例让视频跟随音频消费进度，优先维持声音连续。

| 主时钟选择 | 另一方的同步处理 |
|---|---|
| 音频 | 视频早到时等待，迟到时按策略跳过待显示画面 |
| 视频 | 音频通常需要细微重采样等补偿，同时保持采样连续，处理更复杂 |

两种方式都可行，音频同样有 PTS；采用音频主时钟的依据是输出连续性和同步调整的代价。主时钟应反映实际消费进度，不能直接使用已解码量或已提交量。

### 不能直接把 processedUSecs 当成声卡播放位置

`elapsedUSecs()` 是从 start 起经过的时间，包含 Idle 和暂停，不适合直接作为媒体播放时钟。`processedUSecs()` 表示后端统计的音频处理量，具体统计位置要看实现。

本机 Qt 5.15.2 Windows 后端在提交 waveOut 数据时累加 processedUSecs 所依据的字节量，因此它会包含仍在排队的声音。此程序针对该后端按以下方式估计：

```text
缓冲占用字节 = bufferSize() - bytesFree()
已消费字节估计 = max(0, 已接受字节总量 - 缓冲占用字节)
音频媒体位置 = 本次输出起点 + 已消费字节估计 / PCM 每秒字节数
```

设备按周期归还缓冲，该估计呈阶梯状，精度约为一个周期，不是扬声器物理出声时刻的测量。本例请求 100ms 缓冲，在此后端通常分为五个周期；实际仍以查询结果为准。其他平台后端若更换了计数含义，需要重新核对时钟算法。

视频调度使用该音频位置：早到的图像保留等待；已有多张到期图像时跳过前面的迟到图像，只显示最后一张到期图像。定时器 10ms 唤醒一次，不意味着每 10ms 必须显示一帧，也不意味着视频帧率为 100 fps。

无音轨时使用 QElapsedTimer。若音频在 8 秒结束、视频持续到 10 秒，音频时钟会停在终点；程序确认尾音播完后，从同一个媒体位置接续单调时钟，让剩余画面继续显示。音频结束位置用于辅助这种切换，结束判定仍需结合实际缓冲消费情况。若视频先结束，可以保留最后一张画面，让音频继续播放。

### Idle 不等于文件播放结束

| 设备状态 | 含义 |
|---|---|
| ActiveState | 正在处理音频 |
| SuspendedState | 已暂停，缓冲保留 |
| IdleState | 当前缺少可处理的数据，可能是尚未供给、暂时断供或尾部播放完 |
| StoppedState | 已停止，需结合 error 判断主动停止还是设备失败 |

UnderrunError 表示供给不足，不必等同于永久设备失败。文件读完也不等于设备播放完；播放结束同时要求解码排空、待显示图像消费完、最后一帧时长结束、设备尾音消费完。

## 6. 暂停、停止和 seek 为什么不同

暂停保存当前媒体位置并 suspend 音频，停止 GUI 调度；恢复时 resume 同一批声音并恢复时钟。暂停不清理解码器和待播放结果。

停止丢弃声音与待显示数据，界面回到零。再次播放会重新定位到开头。

### 点击进度条的 API 与信号

进度条范围为 0～10000，媒体目标为 `总时长 × value / 10000`。这个值表示相对时间，不是文件字节偏移。

| API / 信号 | 作用 |
|---|---|
| `QStyle::subControlRect` | 得到实际样式中的滑槽和滑块区域 |
| `QStyle::sliderValueFromPosition` | 将鼠标位置换成进度值，处理范围及方向 |
| `setSliderDown(true/false)` | 标记拖动开始和结束，触发相应信号 |
| `sliderPressed` | 记录原播放意图，必要时暂停 |
| `valueChanged` | 拖动期间显示目标时间，不反复执行 seek |
| `sliderReleased` | 松手后提交一次定位，按原意图恢复播放或保持暂停 |

### seek 的完整关系

```text
GUI：会话编号递增 → 清图像/PCM缓存 → reset 音频 → start 新输出计数
    → 向工作线程发送目标时间
工作线程：目标微秒 + 容器起点 → 换成视频流时间基
    → av_seek_frame(..., AVSEEK_FLAG_BACKWARD)
    → avcodec_flush_buffers(视频) + avcodec_flush_buffers(音频)
    → 清临时包/帧，重建 SwrContext，重置采样时间计数
    → 从定位处重新读包、解码
    → 丢弃目标前的视频，按采样裁掉目标前的音频
GUI：收到目标附近数据 → 重建时钟 → 播放或显示暂停预览
```

`av_seek_frame(input, stream_index, timestamp, flags)` 中 timestamp 使用指定流的 time_base；本例指定视频流，不能直接传微秒数。BACKWARD 允许落到更早的关键帧，以恢复后续图像所需的参考关系。

`avcodec_flush_buffers(context)` 清解码状态，但不清应用队列、Qt 音频缓冲或 SwrContext。三个层次必须分别处理。seek 时清状态与 EOF 时送 nullptr 排空目的不同：前者丢弃旧位置数据，后者把有用的尾部数据取完。

目标落在一张画面的持续区间内时，可以显示覆盖该目标的画面。音频按目标采样下标裁切，一个 AVFrame 可以只保留后半部分，不必整帧保留或整帧丢弃。

会话编号解决另一个问题：即使 GUI 已经清缓存，旧线程结果仍可能排在 Qt 事件队列中。每个结果携带产生时的编号，GUI 只接受当前编号。指针有效不代表它属于当前文件或当前位置。

## 7. 关键调用链与缓存边界

```text
打开：MediaWindow::OpenFile → MediaDecoder::Open
    → avformat_open_input → avformat_find_stream_info → 打开两个解码实例
    → Opened → AudioOutput::Open/Restart → SetOutputRate → ReadRequested

读包：MediaDecoder::Read → av_read_frame → 按 stream_index 选择上下文
    → Send → avcodec_send_packet → Receive 循环 avcodec_receive_frame
    → ConvertVideo 或 PrepareAudio/ConvertAudio → BatchReady

播放：AcceptBatch → TryStart → QTimer::timeout → Tick
    → AudioOutput::Pump → QIODevice::write
    → PositionUs → 选择到期 QImage → VideoView::SetImage → paintEvent

结束：av_read_frame 返回 EOF → 两个解码器送 nullptr 并取到 EOF
    → swr_convert 空输入取尾部 → batch.eof
    → GUI 等图像和设备尾音消费完 → Ended
```

正常情况下提前准备约 150ms 媒体数据，起播音频准备量约 100ms。声画交错读取产生少量画面缓存；它不是把整个视频解码到内存。图像总量上限为 64 MiB/180 张，应用 PCM 上限约两秒，另有设备缓冲和 FFmpeg 内部状态。

达到正常准备量后停止发新的读取请求；异常交错导致某一类数据持续积压时明确报错。独立的读包线程、分轨编码包队列、更细的背压和性能测量属于后续扩展。

本例面向连续时间戳的本地 SDR 视频、第一条视频和音轨。音频使用连续累计采样定位；中途时间戳跳变、动态格式变化、无界网络等待、硬件解码和 HDR 不在此实现范围。
