# 第五阶段：Qt 音频输出、音画同步与进度跳转

## 1. 解码与播放之间还隔着什么

```text
一个 AVFormatContext 顺序读包
    ├─ 视频 AVCodecContext → AVFrame → SwsContext → RGB QImage
    │                                              ↓
    │                                等待显示时机 → VideoView
    └─ 音频 AVCodecContext → AVFrame → SwrContext → S16 交错 PCM
                                                   ↓
                            应用缓冲 → QAudioOutput → 系统/设备
```

FFmpeg 负责得到图像和声音数值，不负责本程序的播放按钮、声卡输出或显示时机。Qt 音频 API 接收的是解码后的 PCM，不是 AAC 包或 MP4 文件。

`AVFormatContext` 一般叫“格式上下文”；本例用于输入，可称“解封装上下文”，保存本次打开媒体的流信息、读取状态和内部缓存。`AVInputFormat` 则描述使用哪一种解封装器。它们都不是音视频解码器。

三个进度必须分开：已经解码的数据、已经提交给设备的数据、设备已经消费的数据。提前解码和提前写入缓冲可以防止断音，但画面不能跟着“已提交量”提前显示。

## 2. 模块、对象与线程

| 模块 | 保存什么、负责什么 | 不负责什么 |
|---|---|---|
| `MediaDecoder` | 容器、两个解码实例、像素转换器、重采样器；读包、转换、定位 | 控件与声音设备 |
| `AudioOutput` | Qt 音频设备、目标格式、PCM 缓冲、已提交量；输出及消费位置估计 | AAC 解码和视频显示 |
| `MediaWindow` | 播放状态、会话编号、待显示图像、时钟与控件 | 执行耗时的 FFmpeg 解码 |
| `VideoView` | 当前拥有像素的 QImage，等比例绘制 | 决定何时切换画面 |
| `ProgressSlider` | 鼠标位置到进度值的映射 | 执行 FFmpeg seek |

MediaDecoder 在 QThread 工作线程中运行。MediaWindow、AudioOutput 和 QWidget 都在 GUI 线程中使用。跨线程信号通过排队连接传递，GUI 不直接操作解码上下文。音频设备与它返回的 QIODevice 也不在两个线程间交替调用。

跨线程结果为 `MediaBatch`：若干 `VideoPicture`、若干 `AudioBlock` 和 eof 标记。Batch 表示“一批结果”，数量并不固定。QImage 与 QByteArray 持有自己的数据；工作线程随后 unref AVFrame，不会破坏 GUI 缓冲。

`Q_DECLARE_METATYPE(MediaBatch)` 让自定义类型接入 Qt 元类型系统；`qRegisterMetaType<MediaBatch>()` 在运行时注册类型及复制、销毁等操作信息，供排队信号保存和传递参数。注册类型不等于创建一个 MediaBatch 对象，也不负责启动线程。

这里一次 Read 对应一次读包，而不是一张画面：音视频包交错出现，一个包也可能暂时没有解码输出。GUI 最多保留一个在途读取请求，并根据声画准备量决定是否继续请求。

## 3. Qt 5 的音频对象分别是什么

### QAudioDeviceInfo：设备描述

它描述设备能力，不保存待播放 PCM。`defaultOutputDevice()` 返回系统默认输出设备的描述；`availableDevices(QAudio::AudioOutput)` 列出可用输出设备。

`isNull()` 不足以覆盖所有后端的无设备情况：本机 Qt 5 Windows 后端在没有实际设备时仍可能给出默认设备描述。还需检查设备列表及最终打开结果。

| API | 参数与结果 | 本例用途 |
|---|---|---|
| `availableDevices(mode)` | mode 为 AudioOutput 或 AudioInput；返回设备描述列表 | 确认存在输出设备 |
| `defaultOutputDevice()` | 返回默认输出设备描述 | 选择本播放器的输出设备 |
| `isFormatSupported(format)` | 输入完整 QAudioFormat，返回是否支持该组合 | 在实际创建输出前检查格式 |
| `supportedSampleRates()` | 返回支持的采样率候选列表，单位 Hz | 48 kHz、44.1 kHz 不支持时继续选择 |
| `preferredFormat()` | 返回后端给出的优选描述 | 可辅助诊断，不能替代实际打开验证 |
| `deviceName()` | 返回设备名称 | 显示协商结果 |

单独支持某个采样率和某个位深，不代表它们与任意声道数的组合都可用，因此最终检查完整 format。

### QAudioFormat：PCM 字节的解释规则

它是一个格式描述值，不持有声音数据，也不执行重采样。

```cpp
format.setCodec("audio/pcm");
format.setSampleRate(48000);
format.setChannelCount(2);
format.setSampleSize(16);
format.setSampleType(QAudioFormat::SignedInt);
format.setByteOrder(QAudioFormat::LittleEndian);
```

| 设置 | 含义 | 必须区分的概念 |
|---|---|---|
| `setCodec("audio/pcm")` | 交给设备的是 PCM | 不是源文件的 AAC 编码 |
| `setSampleRate(rate)` | 每声道每秒的采样数量 | 不是音高，也不是码率 |
| `setChannelCount(2)` | 一个时刻有两个声道采样 | 本例重采样目标明确为 stereo |
| `setSampleSize(16)` | 一个声道的一个采样占 16 位 | 是 bit，不是 byte |
| `setSampleType(SignedInt)` | 按有符号整数解释位模式 | 16 位宽与整数类型共同确定 S16 |
| `setByteOrder(LittleEndian)` | 多字节数值低字节在前 | 不表示左右声道排列顺序 |

Qt 此输出路径接收声道交错 PCM。上述格式的一组同时刻采样是 `L R`，占 `2 × 2 = 4` 字节；48 kHz 每秒占 192000 字节。SwrContext 的输出采样率必须与实际选中的 Qt 格式一致；仅修改 QAudioFormat 不会转换数据。

| 换算 API | 含义 |
|---|---|
| `bytesPerFrame()` | 一组同时刻的所有声道采样共占多少字节，本例为 4 |
| `bytesForDuration(us)` | 某段时长需要的字节量，输入单位为微秒 |
| `durationForBytes(bytes)` | 这些字节对应的时长，返回微秒 |

这里的 frame 指“一组同时刻的声道采样”，不是 FFmpeg 的 AVFrame。一个音频 AVFrame 通常包含很多组这样的采样。

本例只在设备支持的 S16、stereo、小端组合中选择采样率；不支持时明确报错，不把其他格式的数据冒充 S16。

`AudioOutput::Open()` 选择系统默认输出设备，依次尝试 48000、44100 Hz 和设备报告的其他候选采样率，每次检查完整格式组合。返回值是本次选中的输出采样率，不是设备唯一固定的采样率。GUI 通过 `OutputRateRequested` 把它交给解码线程，作为 SwrContext 的目标采样率；实际启动设备由 `Restart()` 完成。

输出采样率表示每声道每秒应交给设备多少个采样。正确重采样会改变采样数量，同时保持媒体时长；仅把原 PCM 按另一采样率播放则会改变速度。

### QAudioOutput：正在输出声音的实例

`QAudioOutput(device, format)` 按指定设备和格式创建工作对象。它不同于设备描述，也不自动识别传入数据的格式。

| API | 作用、参数及注意点 |
|---|---|
| `setBufferSize(bytes)` | 请求设备缓冲大小，单位字节，须在 start 前设置 |
| `start()` | 启动推送模式，返回已经打开的可写 QIODevice 指针 |
| `start(QIODevice*)` | 另一种拉取模式，由 Qt 从调用者提供的可读设备取 PCM；本例不用 |
| `bufferSize()` | 查询实际缓冲大小，可能与请求值不同 |
| `periodSize()` | 每个设备处理周期建议提供的字节量 |
| `bytesFree()` | 当前可接受的空闲字节量；不能当作已经播放的字节总数 |
| `suspend()` | 暂停声音处理，保留缓冲供继续播放 |
| `resume()` | 从暂停状态恢复 |
| `reset()` | 立即丢弃缓冲数据；seek、切文件时使用 |
| `stop()` | 停止输出并释放相关系统资源，不能替代暂停保存状态 |
| `setVolume(value)` | 本输出实例的线性音量，0 为静音，1 为满音量 |
| `state()` / `error()` | 查询设备状态与错误原因 |
| `stateChanged(state)` | 状态变化信号，可用于响应设备异常；本例在 Tick 写入时检查状态 |

`start()` 返回的 QIODevice 属于 QAudioOutput，只借用，不自行 delete。停止、reset 或重新 start 后，旧指针不再用于写入；本例重新取得 sink_。

Qt 5 的 QAudioOutput 在这里负责 PCM 输出。阅读其他版本资料时要核对类的职责，不能直接照搬 Qt 6 的音频输出类组合。

## 4. PCM 怎样真正交到设备

```text
协商 QAudioFormat → 创建 QAudioOutput → setBufferSize → start()
                                                       ↓
                                              得到 QIODevice* sink
                                                       ↓
AudioBlock → 应用缓冲 → 组成一个设备周期 → sink->write(data, bytes)
                                                       ↓
                                              保留未接受的剩余字节
```

`QIODevice::write(const char* data, qint64 bytes)` 接收字节地址与请求长度，返回实际接受的字节数；可能少于请求量，返回 -1 表示错误。它不返回采样数或播放时长。返回 0 时本轮停止写入，等后续 Tick 再尝试，不能忙等。

本例先准备一个 periodSize 大小的块，在 bytesFree 足够时提交。按实际返回值减少待写字节并增加 written_bytes_，未接受的部分仍由 period_ 保存。最后不足一个周期时补静音提交，但媒体结束位置不包括补零。

### 提前提交与供给不足

设备按采样率连续消费 PCM，写入缓冲不等于立即播放。48 kHz、双声道 S16 的 192000 字节对应一秒声音，提前提交仍需要约一秒才能播完。`Pump()` 只在设备有空位时写入，剩余数据留在应用队列；无需等每个 AudioBlock 的 PTS 到达才提交。

这种提前提交方式来自设备的连续消费机制，并不是选择音频主时钟才允许这样做。播放器先将 PCM 的格式、顺序、起点及时间间隙处理正确，再根据已消费量同步视频。

数据供给包括读包、解码、重采样和提交，整体速度要跟得上设备消费；短时耗时波动由缓冲吸收，不要求每次解码都更快。若持续花 120ms 才产出 100ms 音频，缓冲最终会耗尽。

例如设备已有 100ms 音频，下一批在现实时间第 120ms 才到达：前 100ms 正常播放，中间 20ms 断供，第 120ms 才继续播放媒体中第 100ms 之后的声音。内容没有自动丢失，而是晚播放；这不同于媒体本来就有的静音。本例主时钟依赖已消费 PCM，断供期间播放位置不持续增长，视频也会随之等待。

### PCM 的时间信息、静音与数据间隙

音频 AVFrame 同样有起始 PTS，一帧内部的采样按固定时间间隔排列。将起始 PTS 换算为秒，记为 t0，则第 n 个采样对应 `t0 + n / sample_rate`，整帧覆盖的时长为 `nb_samples / sample_rate`；采样数均按每个声道计算。例如从 1 秒开始、48 kHz、每声道 4800 个采样的一块数据，覆盖 `[1.0 秒，1.1 秒)`。

裸 PCM 数组只存采样值，时间信息由 AVFrame 或本例的 AudioBlock 等结构携带。`sink_->write(pcm_data, byte_count)` 没有 PTS 参数：设备按配置的采样率顺序消费字节，播放器需要在提交前处理好时间关系。

AudioBlock 同时保存 PCM 字节与媒体 PTS。AudioOutput 把 PTS 换算成相对于本次输出起点的采样位置：

- 块的起点晚于下一次应写位置：按需补静音，保留音轨起始偏移。
- 块的起点早于下一次应写位置：裁去重叠采样。
- 正好接上：连续写入。

时间间隙按周期逐段填充，不为一段很长的静音一次分配巨大数组。静音的数值与样本格式有关；本例 S16 的静音为全零。

“静音段”和“没有音频数据的时间段”不同：前者仍有占据播放时间的采样；后者需要播放器根据时间戳识别，再决定补静音或处理时间跳变。补静音通常是生成对应数量的 PCM 零值，不要求创建特殊的“静音帧”。音轨可以晚于视频开始、早于视频结束，并不保证覆盖整个视频时段；也不能假定解码器自动补齐所有间隙。

本例保留并补齐音轨起始间隙，之后按连续累计采样定位；流中途任意时间戳跳变尚未完整支持。设备因供给不足而断音，与播放器依据媒体时间戳有意补入静音，是两种情况。

### 音量与静音

`setVolume` 使用线性比例，而人的响度感受不是线性的。滑块值先通过 `QAudio::convertVolume(value, LogarithmicVolumeScale, LinearVolumeScale)` 转换，再提交。静音只将输出设为零，保留用户的音量值；取消静音后恢复它。

## 5. 音频时钟与视频显示

### 公共时间轴

视频 PTS、音频 PTS 各自先从流时间基换成微秒，再减去同一个容器起点。不能把两条轨道分别以自己的首帧归零，否则原本存在的声画偏移会被消除。

Sintel 样本中，视频从零开始，首个实际解码音频帧位于约 0.021333 秒。音频前面留出约 21.33ms 静音后才输出该帧，维持容器描述的关系。

重采样后的 PCM 用“起始时间 + 累计输出采样数 / 输出采样率”定位。累计总数后再换算，避免每一块时长分别舍入再相加导致漂移；重采样器暂未交出的采样不提前计入输出量。

### 为什么选择音频为主时钟

共同时间零点负责对齐各轨道的位置，主时钟负责回答“此刻播到哪里”。主时钟不由哪条流更长决定；音视频可能等长，也可能任意一方先结束。视频帧 PTS 标记应该显示的时刻，本身不会随现实时间前进；最后解码出的 PTS 也不等于当前播放位置。

音频设备按采样率连续消费 PCM。为了追随画面而随意暂停供给、删除或重复采样，可能造成断音、爆音或听得出的变化。视频则可以延长一张画面的显示，或跳过已经迟到的待显示图像。因此，本例让视频跟随音频消费进度，优先维持声音连续。

| 主时钟选择 | 另一方的同步处理 |
|---|---|
| 音频 | 视频早到时等待，迟到时按策略跳过待显示画面 |
| 视频 | 音频通常需要细微重采样等补偿，同时保持采样连续，处理更复杂 |

两种方式都可行，音频同样有 PTS；采用音频主时钟的依据是输出连续性和同步调整的代价。主时钟应反映实际消费进度，不能直接使用已解码量或已提交量。

### 播放位置的三条路径

`MediaWindow::PositionUs()` 返回公共媒体时间轴上的当前位置，单位微秒：

```cpp
if (state_ != State::Playing) return base_us_;
if (audio_clock_) return audio_.PositionUs();
return base_us_ + (clock_.isValid() ? clock_.nsecsElapsed() / 1000 : 0);
```

- 不在播放：返回固定的 `base_us_`，例如暂停位置或 seek 目标，时间不继续推进。
- 使用音频主时钟：返回音频输出层估计的位置，该值已经包含音频本次输出起点，不再加一次 base。
- 使用单调时钟：以 `base_us_` 为锚点，加上 QElapsedTimer 经过的时间；纳秒除以 1000 得到微秒。

`origin_us_` 是各轨道共同减去的文件时间起点；`base_us_` 是当前播放位置或计时锚点，暂停、seek 和时钟切换时会更新，两者用途不同。

### 不能直接把 processedUSecs 当成声卡播放位置

`elapsedUSecs()` 是从 start 起经过的时间，包含 Idle 和暂停，不适合直接作为媒体播放时钟。`processedUSecs()` 表示后端统计的音频处理量，具体统计位置要看实现。

本机 Qt 5.15.2 Windows 后端在提交 waveOut 数据时累加 processedUSecs 所依据的字节量，因此它会包含仍在排队的声音。此程序针对该后端按以下方式估计：

```text
缓冲占用字节 = bufferSize() - bytesFree()
已消费字节估计 = max(0, 已接受字节总量 - 缓冲占用字节)
音频媒体位置 = 本次输出起点 + 已消费字节估计 / PCM 每秒字节数
```

`written_bytes_` 累计设备接受的字节，包含已经消费和仍在排队的部分；队列占用由 `max(0, bufferSize() - bytesFree())` 估计。`AudioOutput::PositionUs()` 在无输出对象时返回起点，暂停时返回已保存的位置；播放时将估算位置限制在有效 PCM 的 `end_us_` 以内，避免末尾补齐周期的静音延长媒体时间。

设备按周期归还缓冲，该估计呈阶梯状，精度约为一个周期，不是扬声器物理出声时刻的测量。本例请求 100ms 缓冲，在此后端通常分为五个周期；实际仍以查询结果为准。其他平台后端若更换了计数含义，需要重新核对时钟算法。

无音轨时使用 QElapsedTimer。若音频在 8 秒结束、视频持续到 10 秒，音频时钟会停在终点；程序确认尾音播完后，从同一个媒体位置接续单调时钟，让剩余画面继续显示。音频结束位置用于辅助这种切换，结束判定仍需结合实际缓冲消费情况。若视频先结束，可以保留最后一张画面，让音频继续播放。

### 视频帧的开始时间、持续时间与缺失时间戳

| VideoPicture 成员 | 含义 |
|---|---|
| `image` | 独立拥有像素的图像 |
| `pts_us` | 画面在媒体时间轴上开始显示的位置 |
| `duration_us` | 预计持续时间；不是解码耗时，也不是下一帧的时间戳 |

例如 `pts_us = 1000000`、`duration_us = 40000`，画面对应 `[1.000 秒，1.040 秒)`。`last_video_end_us_ = pts_us + duration_us` 用于判断最后一张画面的时间是否已经结束；不能刚显示最后一帧就立即认为视频播完。

解码输出优先使用 `best_effort_timestamp`，换算为微秒并减去公共起点；缺失时才使用 `next_video_us_`。持续时间优先使用正值 `frame_->duration`，否则按猜测帧率估算，并保证换算后至少一微秒：

```text
当前帧开始时间 = 有时间戳时按时间戳，否则用上次估计
当前帧持续时间 = 有有效 duration 时使用，否则用帧率估计
next_video_us_ = 当前帧开始时间 + 当前帧持续时间
```

`next_video_us_` 只是下一帧时间戳缺失时的备用值，没有提前读取下一帧。下一帧有自己的时间戳时仍以它为准。正常切换画面依据下一帧的 PTS 是否到期，不是每次显示后固定等待 duration；QImage 也不会在 duration 到期后自动消失。

### Idle 不等于文件播放结束

| 设备状态 | 含义 |
|---|---|
| ActiveState | 正在处理音频 |
| SuspendedState | 已暂停，缓冲保留 |
| IdleState | 当前缺少可处理的数据，可能是尚未供给、暂时断供或尾部播放完 |
| StoppedState | 已停止，需结合 error 判断主动停止还是设备失败 |

UnderrunError 表示供给不足，不必等同于永久设备失败。文件读完也不等于设备播放完；播放结束同时要求解码排空、待显示图像消费完、最后一帧时长结束、设备尾音消费完。

## 6. 播放状态机与缓冲条件

### 状态的含义和转换节点

State 是播放器自己的状态，不是 QAudioOutput 的设备状态。

| 状态 | 含义 |
|---|---|
| `Empty` | 初始状态，尚未打开媒体 |
| `Buffering` | 打开文件或 seek 后，目标位置的数据尚未准备好 |
| `Playing` | 正在推进播放位置并调度音视频 |
| `Paused` | 暂停推进时间，保留位置、画面及待播放数据 |
| `Stopped` | 主动停止，位置归零并清掉声音与画面 |
| `Ended` | 自然播放结束，位置停在末尾 |
| `Error` | 发生错误，停止播放并保留错误信息 |

| 触发位置 | 状态变化 | 关键动作 |
|---|---|---|
| `OpenFile()` | → Buffering | 清理上一媒体，后台打开文件，默认准备好后播放 |
| `StartSeek()` | → Buffering | 清掉旧位置的数据，记录目标及定位后的播放意图 |
| `TryStart()` 条件通过 | Buffering → Playing 或 Paused | 根据 `play_after_buffering_` 播放或显示暂停预览 |
| `TogglePlayback()` | Playing → Paused | 保存位置、suspend 音频、停止定时器 |
| `TogglePlayback()` | Paused → Playing | resume 音频、重启计时和定时器，并调用 Tick |
| `TogglePlayback()` | Buffering → Buffering | 只反转 `play_after_buffering_`，继续准备数据 |
| `TogglePlayback()` | Stopped / Ended → Buffering | 调用 `StartSeek(0, true)` 从头准备重播 |
| `Stop()` | 已打开媒体的状态 → Stopped | 丢弃待播放数据、归零并清空画面 |
| `Tick()` 播完判定通过 | Playing → Ended | 固定最终位置，停止定时器 |
| `Fail()` | → Error | 停止调度、关闭声音输出并清理画面队列 |

`state_` 描述现在处于什么状态；`play_after_buffering_` 描述数据准备好之后是否播放。`StartSeek(target, play_after)` 将参数存入这个成员，是为了供异步解码返回后的 TryStart 使用。处于 Buffering 时，PositionUs 返回固定的 base_us_，Tick 不推进播放。

### TryStart 怎样判断“准备好”

Try 表示“尝试”，不是 C++ 的 try/catch。TryStart 只处理 Buffering，其他状态直接返回。每次收到有效的 BatchReady，GUI 先 AcceptBatch 保存数据，再调用 TryStart；缓冲条件未满足就返回，保留 Buffering，随后继续请求数据，不在函数内阻塞等待。

第一项要求是 `pictures_` 至少有一张画面。队列为空但尚未 EOF 时继续等待；已经 EOF 仍为空，则报“定位后没有可显示的画面”。

第二项是音频满足以下任意条件：

| 条件 | 允许开始的原因 |
|---|---|
| `!audio_.IsOpen()` | 没有启用音频输出，无需等待 PCM |
| `eof_` | 两个解码器和重采样器已经排空，不能继续等待更多数据 |
| `BufferedEndUs() >= base_us_ + 100000` | 音频已准备到当前起点后至少 100ms |
| 已知音轨末尾，且 `BufferedEndUs() + 1000 >= audio_end_us_` | 音频基本已到末尾，允许剩余不足 100ms；容差为 1ms |

例如目标是 10 秒，普通情况下要求至少一张视频画面，且音频准备到 10.1 秒。这里的 BufferedEndUs 是有效 PCM 在媒体时间轴上的结束位置，不是设备已播放的位置；起始间隙由输出层补齐。

两项通过后，才真正执行离开 Buffering 的赋值：

```cpp
state_ = play_after_buffering_ ? State::Playing : State::Paused;
```

进入 Playing 时启动计时和定时器，之后由 Tick 提交 PCM 和显示画面。进入 Paused 时，主动取出一张图调用 SetImage，显示定位预览并暂停音频；因为暂停时 Tick 不工作，预览不能等待定时器更新。准备好不要求 PCM 已经提交给设备。

本例只在打开文件和 seek 时进入 Buffering。Playing 期间暂时缺少数据不会自动切换为 Buffering，尚未实现完整的播放中重新缓冲状态切换。

### 暂停、停止与拖动进度条

暂停保留解码器、队列和设备缓冲，恢复时继续播放同一批声音；停止丢弃声音与待显示数据并归零，再次播放会从头 seek。两者不能用同一种清理方式替代。

进度条范围为 0～10000，目标位置为 `总时长 × value / 10000`，表示媒体时间，不是文件字节偏移。

| API / 信号 | 作用 |
|---|---|
| `QStyle::subControlRect` | 得到实际样式中的滑槽和滑块区域 |
| `QStyle::sliderValueFromPosition` | 将鼠标位置换成进度值，处理范围及方向 |
| `setSliderDown(true/false)` | 标记拖动开始和结束，触发相应信号 |
| `sliderPressed` | 保存 `resume_after_drag_`；若正在 Playing，调用 TogglePlayback 暂停 |
| `valueChanged` | 按住拖动期间只更新目标时间文字，不执行 seek 或解码预览 |
| `sliderReleased` | 调用 StartSeek，松手后才执行一次定位 |

```text
原来播放：Playing → 按下后 Paused → 松手后 Buffering → Playing
原来暂停：Paused  → 拖动时 Paused → 松手后 Buffering → Paused（显示目标预览）
```

`resume_after_drag_` 保存按下前的播放意图，松手时传给 StartSeek；本例没有单独的 Dragging 状态。按住期间画面通常停在按下时的位置，滑块的目标值不等于已经执行了定位。

实现边界：若按下时本来是 Buffering，当前 sliderPressed 没有强制关闭缓冲后的自动播放意图；缓冲可能在尚未松手时完成并进入 Playing。因此不能将“拖动期间必然是 Paused”推广到所有状态。

## 7. seek 的调用链、定位单位与缓存清理

### 从界面到解码线程再返回

```text
GUI：sliderReleased 或 SeekTo()
    → StartSeek(target, play_after)
    → ++session_，停止定时器，ClearPending(target)，audio_.Restart(target)
    → 进入 Buffering，保存 play_after_buffering_，标记请求在途
    → SeekRequested(target, session)

工作线程：MediaDecoder::Seek()
    → 目标微秒 + origin_us_ → 换算为视频流时间基
    → av_seek_frame(..., AVSEEK_FLAG_BACKWARD)
    → avcodec_flush_buffers(视频、音频)
    → ResetDecodeState(target)：清临时数据、释放重采样器、重置计数
    → Seeked(session)

GUI：核对 session → 清在途标记 → RequestData() → ReadRequested
工作线程：Read → 读包、解码 → 裁去目标之前的输出 → BatchReady
GUI：核对 session → AcceptBatch → TryStart
    → 不够则继续请求；足够则播放或显示暂停预览
```

SeekRequested 通过 QueuedConnection 在解码线程执行；Seeked 只表示定位和清理完成，不代表目标画面已经解码好。重采样器在 ResetDecodeState 中释放，在定位后的第一张音频帧到达时由 PrepareAudio 重新创建。

StartSeek 把目标限制在 `[0, max(0, duration_us_ - 1000)]`，避免主动定位到总时长的精确末端。`std::clamp<qint64>(value, low, high)` 返回范围内的值，越界时返回对应边界；1000 微秒是 1ms。

### av_seek_frame 的参数和结果

```cpp
av_seek_frame(input_.get(), video_stream_->index,
              timestamp, AVSEEK_FLAG_BACKWARD);
```

| 参数 | 含义 |
|---|---|
| `input` | 当前媒体的解封装上下文，操作后续读取位置 |
| `stream_index` | 定位依据的流；本例选择视频流 |
| `timestamp` | 指定流时间基中的目标时间戳，不是秒数或帧编号 |
| `flags` | 定位方向和方式；本例按时间向目标之前找关键帧 |

本例用 `av_rescale_q(position_us + origin_us_, kUs, video_stream_->time_base)` 计算 timestamp。若时间基为 1/1000，文件时间轴第 10 秒对应 10000；不能直接把微秒数传入。如果 stream_index 为 -1，则由 FFmpeg 选择默认流，timestamp 使用 AV_TIME_BASE 单位，即微秒。

BACKWARD 指落点在目标时间之前或等于目标，不是要求相对当前播放位置倒退。例如从第 2 秒跳到第 10 秒，也可以使用 BACKWARD：若前一个关键帧在第 8 秒，就从第 8 秒附近读包、顺序解码到目标。AVSEEK_FLAG_ANY 允许非关键帧落点，但不消除后续解码的参考依赖。

指定视频流不表示只移动视频：操作的是整个解封装上下文，之后 av_read_frame 仍会取出音频包和视频包。返回值大于等于零表示成功，小于零表示错误；成功不返回实际落点时间，也不代表已经输出目标帧。实际定位能力取决于输入和解封装器是否支持 seek。

### 各层缓存必须分别处理

| 数据所在层 | seek 时的处理 |
|---|---|
| input_ 内部的解封装包缓存、读取状态 | av_seek_frame 内部处理 |
| 已经读到应用手里的 AVPacket / AVFrame | ResetDecodeState 中调用 unref；不会因 seek 自动失效 |
| 音视频 AVCodecContext 内部的参考与输出状态 | 分别调用 avcodec_flush_buffers |
| SwrContext 内部延迟采样与累计采样计数 | 释放转换器并重置计数，后续按实际帧参数重建 |
| GUI 视频队列、软件 PCM 队列、设备缓冲 | ClearPending 和 AudioOutput::Restart 分别清理 |
| 已经排入 Qt 事件队列的旧结果 | 无法靠清缓存撤回，通过 session 编号拒收 |

seek 清状态是丢弃旧位置的数据；EOF 时送 nullptr 排空是取完有用的尾部数据，不能混用。只调用 av_seek_frame，不足以清除解码器和播放器里已经持有的数据。

session 不是时间戳，而是本次打开或定位的代次。GUI 发起 seek 时先递增，后台结果携带生成时的编号；即使旧 Read 随后才返回，也不会被当成目标位置的新数据。

### 从关键帧位置推进到精确目标

定位到关键帧后仍须正常送包解码，以恢复参考关系；不能直接丢掉目标之前的所有视频编码包。过滤发生在解码输出之后：

- 视频：若 `pts + duration <= target`，不交给界面；若画面覆盖目标，则将交付的开始位置设为 target，并保留剩余持续时间。例如画面覆盖 9.98～10.02 秒，定位到 10 秒时交付 10.00～10.02 秒这一段。
- 音频：重采样后把目标时间换成输出采样下标，向上取整并裁掉目标之前的采样。一个 AVFrame 可以只保留后半部分，不必整帧取舍。

GUI 的播放起点和 AudioOutput 的消费计数起点都设为同一个 target，后续声画继续使用公共媒体时间轴。

## 8. 数据请求与 Tick 调度

### 从 OpenFile 到自动播放的调用链

`OpenFile(path)` 是自动播放入口：先清理上一媒体，进入 `Buffering`，设置 `play_after_buffering_ = true`，然后异步打开文件。函数返回不表示已经开始出声或显示画面；数据准备好后由 `TryStart()` 进入 `Playing`，无需再按播放按钮。`show()`、`raise()` 只负责显示和抬起窗口。

```text
GUI：MediaWindow::OpenFile(path)
    → ++session_，停止定时器，关闭音频输出，ClearPending(0)
    → Buffering，保存准备好后自动播放的意图
    → OpenRequested(path, session)

解码线程：MediaDecoder::Open()
    → avformat_open_input → avformat_find_stream_info
    → OpenCodec：创建并打开视频、音频解码实例
    → Opened(session, duration, has_audio, audio_end)

GUI：收到 Opened，核对 session
    → 有音轨：audio_.Open() 协商格式
      → OutputRateRequested → 解码线程 SetOutputRate()
      → audio_.Restart(0) 准备输出设备
    → RequestData → ReadRequested

解码线程：MediaDecoder::Read()
    → av_read_frame → 按 stream_index 选择解码上下文
    → Send → avcodec_send_packet → Receive 循环 avcodec_receive_frame
    → 视频：ConvertVideo → RGB QImage；音频：PrepareAudio/ConvertAudio → PCM
    → BatchReady(session, batch)

GUI：核对 session，清除在途标记
    → AcceptBatch：视频放入 pictures_，音频交给 audio_.Append()
    → TryStart：检查画面和音频准备量，满足后进入 Playing、启动定时器
    → Tick：按当前播放位置和设备空位输出
    → RequestData：需要更多数据时继续请求
```

播放器构造时先调用 `ConnectDecoder()` 建立信号连接、将解码器移入工作线程，再调用 `thread_.start()` 启动线程。打开文件和读包请求通过排队连接执行，结果再返回 GUI；这些箭头包含线程切换，不是同一函数里的同步调用。输出采样率设置请求先于读包请求排队，无音轨时跳过音频设备初始化。

解码结果先进入应用缓存，实际输出由 `Tick()` 调度：

```text
音频：audio_.Pump() → sink_->write(PCM) → QAudioOutput → 系统/设备
视频：检查画面 PTS → VideoView::SetImage → update → paintEvent → drawImage
```

### 两条互相配合的调用链

```text
数据准备：RequestData → ReadRequested → Read → BatchReady
        → AcceptBatch → TryStart → Tick → RequestData

定时消费：QTimer::timeout → Tick
        → Pump → PositionUs → 选择画面 → RequestData → UpdateControls
```

这是跨线程事件驱动的请求链，不是同步递归，也不是无限忙循环。一次 Read 读一个包，Send/Receive 可能产生零到多个输出；BatchReady 返回后才允许发下一次请求。

`RequestData()` 在文件未打开、已有请求在途、已 EOF，或状态既不是 Buffering 也不是 Playing 时直接返回。允许请求时：Buffering 持续准备启动数据；Playing 仅在音频或视频预读不足时继续请求。

视频检查之一是 `pictures_.back().pts_us < position + 150000`，含义为最后一张待显示图的开始时间还没达到当前位置后 150ms。它近似衡量预读范围，不是该画面的显示条件，也不是严格的队列时长上限。音频也按准备结束位置检查，并避免为了已经结束的音轨继续请求。

缓存够用时，不再发下一个 Read；Tick 仍持续消费，随后发现不足就重新发起请求。用户暂停后定时器停止，RequestData 也被状态条件拦住；已经在途的 Read 可能返回并缓存，但不会因此持续解码或恢复播放。

### Tick 每次做什么

1. 仅在 Playing 执行；其他状态直接返回。
2. 判断音频是否准备到末尾，将结果传给 Pump，按设备空位提交 PCM；尾块不足一个周期时允许补零提交。
3. 若当前使用音频时钟，且音频数据已到末尾、Drained 为真，从音频结束位置接续单调时钟。
4. 获取一次 PositionUs，取出 PTS 不晚于该位置的画面；若后一张也到期，跳过前一张，只显示最后一张到期画面。未来的画面留在队列中。
5. 检查播放是否结束；然后 RequestData 补充数据，UpdateControls 更新界面。

例如当前位置为 1010ms，队列 PTS 为 920、960、1000、1040ms，则跳过前两张，显示 1000ms，保留 1040ms。没有画面到期时继续保留当前图片。

定时器间隔为 10ms，PreciseTimer 表示定时精度策略，不保证绝对准时；播放位置来自时钟，而不是每次回调加 10ms。BatchReady 和恢复播放时也会直接调用 Tick，因此 Tick 不只有定时器一个入口，也不保证每次调用都更新画面。

显示链为 `SetImage → update → paintEvent → QPainter::drawImage`。SetImage 保存图像并请求重绘；FramePresented 只是“已交给画布”的通知，当前由测试中的 QSignalSpy 监听，不负责驱动绘制，也不证明屏幕此刻已经完成显示。没有接收者的 Qt 信号可以正常发出。

### 音频到末尾、设备播完与整体结束

`audio_finished` 表示 eof_ 已成立，或有效 PCM 已基本准备到已知音轨末尾；它不表示声音已经播完。`audio_.Drained()` 表示应用 PCM、未写完的周期块和设备缓冲均已空，无音频输出时直接返回 true；暂时断供也可能满足 Drained，所以时钟切换必须同时检查 audio_finished。

整体结束要求四项同时成立：`eof_`、视频队列为空、当前位置不早于 `last_video_end_us_`、音频已 Drained。满足后固定最终位置、进入 Ended 并停掉定时器。

```text
av_read_frame 返回 EOF
    → 两个解码器送 nullptr 并取到 EOF
    → swr_convert 空输入取完尾部 → batch.eof
    → GUI 等最后一帧持续时间结束和设备尾音消费完 → Ended
```

### 缓存与输入边界

起播音频准备量约 100ms，正常播放预读约 150ms，设备另外请求约 100ms 缓冲；三者分属启动条件、读取调度和设备输出，不是同一个缓存参数。图像总量上限为 64 MiB/180 张，应用 PCM 上限约两秒，另有 FFmpeg 内部状态。

达到正常准备量后停止发新请求；异常声画交错导致某类数据持续积压时明确报错。独立读包线程、分轨编码包队列、更细的背压和性能测量属于后续扩展。

本例面向连续时间戳的本地 SDR 视频、第一条视频和音轨。音轨起始间隙可保留；中途任意时间戳跳变、动态格式变化、无界网络等待、硬件解码和 HDR 不在此实现范围。
