# 第三阶段：播放时钟、Qt 绘制与线程

## 1. 解码、调度、绘制是三件事

| 环节 | 负责什么 | 相关对象 |
|---|---|---|
| 解码 | 把编码数据还原成像素，得到帧的呈现时间 | FFmpeg、AVFrame |
| 调度 | 决定哪一帧现在应该交给画面显示 | PTS、播放时钟、待显示帧 |
| 绘制 | 把选中的图像画到窗口区域 | QImage、QPainter、QWidget |

解码完成不代表应该立即显示。五秒的视频可能很快解完，但正常播放仍需要五秒。窗口重绘也不一定需要下一帧：调整窗口大小、窗口被遮挡后恢复，可能只是重画当前图像。

视频帧率、界面重绘频率、屏幕刷新率是不同概念。8 fps 的视频可以在 60 Hz 屏幕上播放，屏幕会在多个刷新周期里保持同一帧。

## 2. 媒体时间与播放时钟

PTS 是媒体时间轴上的位置，不是电脑当前日期，也不是解码耗时。时间戳先按流时间基换算成本例统一使用的微秒。

本地单视频播放可把首帧呈现时间作为零点：

```text
帧的目标播放位置 = 当前帧 PTS - 首帧 PTS

源 PTS：5.000 秒、5.125 秒、5.250 秒
播放位置：0 秒、0.125 秒、0.250 秒
```

首帧就绪时启动播放时钟，打开文件和等待首帧的时间不计入播放进度。无声播放可以使用单调计时器 `QElapsedTimer`；单调时间适合计算经过的时长，不随系统日期校准而跳变。

| 比较结果 | 含义 |
|---|---|
| 帧的目标位置 > 当前播放位置 | 这帧还没到显示时间，保留并等待 |
| 帧的目标位置 ≤ 当前播放位置 | 可以显示；若已经落后，属于迟到帧 |

可变帧率视频的帧间隔不固定，应依据每帧时间戳判断，不能只按平均帧率每隔固定时间换图。本例迟到帧立即交给画布，不实现主动丢帧策略；解码跟不上时仍可能卡顿。

## 3. 定时器与暂停恢复

`QTimer` 的职责是定期唤醒事件处理，不是充当精准计数器。设置 10 ms 不保证每次恰好经过 10 ms；事件循环繁忙时，回调可能延后。

```text
本例播放位置 = 已累计的播放时间 + 本次运行的实际经过时间
```

不能在每次 timeout 时简单执行“进度 += 10 ms”，否则调度误差会累积。`Qt::PreciseTimer` 可以提高定时精度，但不是实时保证；每次唤醒仍需要读取实际时钟。

暂停时记录当前位置并停止定时唤醒；恢复时重新计时，再加上暂停前已经累计的时间。暂停期间经过的现实时间不计入播放进度。暂停后的窗口仍能处理重绘、按钮和关闭事件。

最后一帧也有显示时长：解码器输出 EOF 后，应保留它到“最后一帧的目标位置 + 帧时长”，再标记播放结束。输入结束、解码结束、播放结束是三个不同的时刻。

## 4. QImage 的像素与所有权

`QImage` 描述内存中的图像，可以直接访问像素；它不等于窗口，也不负责自动显示。

```cpp
QImage image(rgb->data[0], rgb->width, rgb->height,
             rgb->linesize[0], QImage::Format_RGB888);
```

`QImage::Format_RGB888` 对应这里的 FFmpeg RGB24：每像素按 R/G/B 存三个字节。`bytesPerLine` 参数应传实际行跨度，不能默认使用宽度乘三。

这个构造函数借用外部像素，不会自动复制整张图。若 FFmpeg 在界面绘制前复用了缓冲区，画面就可能被篡改或访问失效内存。

`image.copy()` 创建拥有独立像素的 QImage，之后 FFmpeg 可以安全复用其缓冲。普通 QImage 值复制通常采用隐式共享，不会每次都深拷贝；只读传递可以共享同一块已拥有的像素内存，修改时可能发生分离。跨线程传递后，本例不再修改这张图。

## 5. QWidget 与 QPainter

| API / 概念 | 职责 |
|---|---|
| `QWidget::update()` | 请求事件循环安排重绘，多次请求可能合并 |
| `paintEvent()` | Qt 需要重绘窗口时调用的事件处理函数 |
| `QPainter` | 执行填色、画图、文字和坐标变换等绘制操作 |
| `drawImage()` | 把 QImage 绘制到目标矩形 |
| `Qt::KeepAspectRatio` | 缩放时保持图像宽高比 |

视频画布保存当前 QImage，在 paintEvent 中绘制。解码和等待时间不放进 paintEvent，否则重绘可能阻塞或反复触发解码。

保持比例的适配：缩放系数取 `min(窗口宽/图像宽, 窗口高/图像高)`，把缩放后的图像居中，剩余区域填黑。窗口尺寸改变时只需重新计算绘制区域，不需要重新解码。这里按方形像素处理，像素宽高比与旋转元数据属于额外的显示信息。

把图像交给画布并调用 update，不表示像素此刻已出现在显示器上；后面还有 Qt 的重绘事件和窗口系统的显示过程。程序的 FramePresented 信号记录的是交给画布的时间点。

## 6. 线程归属与跨线程信号

GUI 线程处理事件循环、按钮和窗口绘制；解码线程处理打开文件、读包、解码与像素转换。后台耗时工作不直接占用 GUI 线程，界面才能持续响应。

| 对象或操作 | 所在线程 |
|---|---|
| PlayerWindow、VideoView、播放定时器 | GUI 线程 |
| VideoDecoder 及 FFmpeg 解码资源的使用 | 解码线程 |
| `QThread` 对象本身 | 创建它的 GUI 线程；它管理另一个线程的执行 |

`decoder_->moveToThread(&thread_)` 将 decoder_ 这个 QObject 派生类的对象实例归属到 thread_ 管理的工作线程，不是把整个类绑定过去。线程归属决定对象的事件和排队的槽调用由哪个线程处理；这个操作本身不启动线程，也不执行解码。

`thread_.start()` 启动独立的工作线程。默认实现是在新线程执行 `QThread::run()`，再由 run 调用 `exec()` 运行事件循环。有事件或排队的槽调用时处理，没有任务时等待，不会一直空转。如果重写 run，是否运行事件循环由重写后的实现决定。

```text
GUI 线程：执行 PlayerWindow 构造函数 → thread_.start() → 继续执行构造函数
                                           ↓
工作线程：                          QThread::run() → exec() → 处理事件
```

构造函数及 start 后面的代码仍在 GUI 线程执行；QThread 对象本身也仍归属于 GUI 线程。`moveToThread()` 不会让普通 C++ 调用自动切换线程：在 GUI 线程直接调用 `decoder_->Read(session_)`，Read 仍会在 GUI 线程执行。

`Qt::QueuedConnection` 把调用作为事件投递到接收对象所属线程，接收方的事件循环再执行槽函数。后台返回图像时，跨线程的自动连接同样会排队，让界面在 GUI 线程接收结果。

本例由三者配合完成后台解码：moveToThread 指定接收对象的线程归属，start 启动工作线程及默认事件循环，QueuedConnection 将 Read 的调用投递过去。

```text
GUI 发出 FrameRequested
    → 解码线程执行 Read
    → 发出 FrameReady（独立 QImage + 时间信息）
    → GUI 保存待显示帧，按播放时钟判断时机
```

“信号已发出”不等于“槽已执行”。线程与像素内存所有权必须一起考虑，不能发送一个马上就被释放的裸像素指针。

## 7. 有限缓存、状态与关闭

逐帧发信号不代表缓存天然有限。如果解码远快于播放，大量图像会积压在事件队列中，占用内存。

本例使用按需取帧：当前帧交给画布后才请求下一帧。应用侧只保留当前显示图像和最多一张待显示图像，不因文件变长而积累整段视频；解码器内部仍有参考帧等缓存。

暂停时允许已经请求的下一帧返回，但保留它而不继续显示、请求更多帧。这样不需要暂停线程或强行挂起解码函数。

播放器状态区分：未打开、正在打开、播放中、已暂停、播放结束、出错。状态决定时钟是否前进、按钮是否可用。重新播放可以重新打开文件，让解码和时钟状态从头建立。

切换文件后，旧文件的结果可能仍在事件队列里。每次打开使用不同 session 编号，接收结果时核对编号，避免旧帧覆盖新文件画面。

`requestInterruption()` 发出协作停止请求，不会强制中断 C++ 代码；解码循环和 FFmpeg 中断回调需要检查它。`quit()` 请求退出线程事件循环，`wait()` 等待线程结束。线程停止后再销毁资源，避免工作仍在进行时释放对象。

## 8. 时间信息缺失的含义

正常情况下使用帧的 best_effort_timestamp；缺失时只能根据前一帧和估计时长构造时间。帧时长缺失时可按帧率估算；帧率也未知时，本例采用 25 fps。估算只保证基本推进，不代表恢复出了文件原本准确的节奏。

解码、时钟调度和 CPU 绘制已足以构成基本无声播放器。GPU 渲染是另一种绘制实现，硬件解码是另一种还原编码数据的实现，二者不应混为一谈。

## 9. VideoDecoder 的 API 调用关系

### 对象与数据流

| 成员 | 在调用链中的作用 |
|---|---|
| `input_`、`stream_` | 输入上下文及所选视频轨道；用于读包、筛选轨道和解释时间单位 |
| `context_` | 持续使用的解码实例，保留参考图像及尚未输出的结果等状态 |
| `packet_` | 接收本次读出的编码包，送入解码器后释放调用方的数据引用 |
| `frame_` | 接收一帧解码结果，转换完成后释放当前像素引用 |
| `rgb_`、`scaler_` | RGB 目标帧与像素转换上下文，供 ConvertFrame 使用 |

数据经过的环节为：

```text
av_read_frame                  提取 AVPacket
    → 筛选 stream_index        只保留选中视频轨道的包
    → avcodec_send_packet      将包提交给 context_
    → avcodec_receive_frame    从 context_ 取得一帧 AVFrame
    → sws_scale_frame          将源像素转换成 RGB24
    → QImage(...).copy()       得到拥有独立像素的图像
    → FrameReady               把图像、PTS、时长交给 GUI
    → Tick                     根据播放时钟判断是否到显示时间
    → SetImage / update        保存当前图像，请求重绘
    → paintEvent / drawImage   绘制到窗口
```

这条箭头表示数据关系，不表示一次 Read 必须把每个 API 各调用一次。send 成功不保证立即有输出，receive 成功得到的帧也不一定对应刚送入的包。

### Open：每次打开输入时建立解码状态

```text
avformat_alloc_context
    → 设置 interrupt_callback，供耗时读取检查关闭请求
avformat_open_input
    → 打开输入、识别容器
avformat_find_stream_info
    → 探测并补齐轨道参数
遍历 input_->streams
    → 选择第一条 codec_type 为 VIDEO 的轨道
avcodec_find_decoder(stream_->codecpar->codec_id)
    → 查找该编码对应的解码实现
avcodec_alloc_context3
    → 创建本次解码实例 context_
av_packet_alloc / av_frame_alloc / sws_alloc_context
    → 创建包、源帧、RGB 帧及像素转换上下文
avcodec_parameters_to_context
    → 将轨道编码参数复制到 context_
设置 pkt_timebase、thread_count → avcodec_open2
    → 声明输入时间单位并初始化解码器
av_guess_frame_rate / av_inv_q / av_rescale_q
    → 估算缺失帧时长时使用的微秒间隔
Opened → GUI 发出 FrameRequested → 解码线程执行 Read
```

`Open()` 建立的 input_ 和 context_ 在多次 `Read()` 之间持续存在，不是每取一帧就重新打开文件或创建解码器。

### Read：先取输出，需要输入时才读包

```text
进入 Read(session)，检查会话、解码上下文及中断请求
    ↓
外层 while：尝试取得一帧输出
    ↓
avcodec_receive_frame(context_, frame_)
    ├─ 返回 0：取得一帧
    │    → av_rescale_q：把帧 PTS、时长换算为微秒
    │    → ConvertFrame：转换为独立 QImage
    │    → av_frame_unref：释放本次源帧引用
    │    → emit FrameReady，return，结束本次 Read
    │
    ├─ 返回 EAGAIN：当前需要更多输入
    │    → 内层 do/while：av_packet_unref → av_read_frame
    │        ├─ 非目标轨道的包：释放后继续读
    │        ├─ 目标视频包：avcodec_send_packet(context_, packet_)
    │        │               → av_packet_unref
    │        └─ 输入 EOF：avcodec_send_packet(context_, nullptr)
    │                       → draining_ = true
    │    → 回到外层 while，再次 receive
    │
    ├─ 返回 EOF：解码器输出已取完，emit Ended，return
    └─ 其他错误：Check 抛出异常，捕获后 emit Failed
```

外层循环协调送包与取帧；内层循环只负责跳过其他轨道的包。一次 Read 可能送入多个视频包才得到一帧，也可能直接取到解码器已有的输出而完全不读包。读包或送包出错同样会进入错误处理，不会继续当作正常数据使用。

本例在 receive 返回 EAGAIN 后才 send。正常 send/receive 契约不允许两端同时因 EAGAIN 拒绝推进，因此这里可以继续提交输入。一般写法若先 send 并收到 EAGAIN，需要先取输出，再重送同一个尚未被接受的包。

输入 EOF 后只成功提交一次空包。之后各次 Read 继续取出剩余帧，直到 receive 返回 EOF；`draining_` 防止继续索取输入。没有得到过任何画面就结束时，本例报告“视频没有可显示的帧”。Ended 表示解码结束，GUI 仍需让最后一帧保持到其结束时间。

### 输出顺序与时间换算

对于本例正常的 MP4/H.264 解码，包按解封装器提供的解码顺序提交，解码器处理参考依赖与输出重排，receive 返回用于呈现的帧顺序。它不等待现实时间到达 PTS，也不是将包按 PTS 排序后解码；应用无需手动对这些包排序。

因此，读包顺序可能是 `I0 → P2 → B1`，输出帧顺序则是 `I0 → B1 → P2`。显示调度使用输出帧自身的 best_effort_timestamp，不能拿最近一次输入包的 DTS 或 PTS 代替。时间戳缺失或异常不等于可以任意排序修复；本例的缺失时间处理见第 8 节。

`av_rescale_q(value, source_base, target_base)` 按两个时间基换算整数时间值：本例由 stream_->time_base 换算到 `{1, AV_TIME_BASE}`，结果单位为微秒。它只换算数值，不等待、不推进播放时钟。

### ConvertFrame 与 GUI 的衔接

```text
av_frame_unref(rgb_)                  释放上次转换结果
设置 rgb_ 的尺寸、RGB24 及颜色属性    声明目标图像规格
sws_scale_frame(scaler_, rgb_, frame_) 转换像素
QImage(..., linesize, Format_RGB888)   借用 RGB 像素
image.copy()                         复制到 QImage 自有内存
return QImage                        返回给 Read，再通过信号交给 GUI
```

GUI 接收 FrameReady 后保存待显示图像并调用 Tick；QTimer 的 timeout 也会调用 Tick。Tick 只在播放中且帧的目标时间已到时换图，随后发出下一次 FrameRequested。尚未到时间或正在暂停时，保留待显示帧。

跨线程信号按事件投递，所以上图的连续箭头不表示所有步骤都在同一个线程或同一次函数调用中执行。当前图像交给画布后，后台可以准备下一帧；每次请求最多交出一帧，不会一次把整段视频解码并堆入 GUI 事件队列。
