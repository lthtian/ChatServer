# 第六阶段：聊天视频收发与播放

本阶段把第五阶段播放器接入 Qt 聊天客户端。视频按普通文件保存，接收方点击消息后，使用已校验的完整本地 MP4 播放；缓存缺失或损坏时先下载。单文件上限为 100 MiB。

## 1. 两条网络通道，各自传什么

| 通道 | 内容 | 作用 |
|---|---|---|
| 已登录的聊天 TCP 连接 | JSON 控制请求、媒体元数据、消息通知 | 确认用户和会话，申请传输授权，发布聊天消息 |
| HTTP 连接 | MP4 的原始文件字节 | 上传到磁盘、从磁盘下载 |

这里发送的是包含编码数据的完整 MP4，没有在上传前解码成图片或 PCM。只有接收方开始播放时，FFmpeg 才执行已经学过的解封装、解码、转换与同步。

服务端返回的传输描述包含 `method`、`url` 和 `headers.Authorization`。其中 Bearer 凭证关联登录会话和操作权限；知道 `media_id` 不代表获得读取权限。凭证过期或聊天连接断开后，需要重新建立有效请求。

TCP 是字节流，一次 `readyRead` 不一定对应一条 JSON。`MyTcpClient::read()` 累积数据，识别完整 JSON 后交给业务处理；HTTP 文件内容不经过这个 JSON 缓冲区。

### 模块拆分与连接拆分

HTTP 本身也通过 TCP 传输，但文件请求使用独立于聊天连接的通道。大文件与聊天消息如果混在同一条 TCP 字节流中，后面的消息可能等待前面的文件字节；独立连接便于分别收发、取消和设置超时，但仍共享网络带宽。这是本项目的设计选择，不是 TCP 要求文件必须单独连接。

`ChatService` 接收聊天控制请求，将媒体相关操作交给 `MediaService::request()`；`MediaService` 同时负责媒体授权、资源状态以及 HTTP 文件接收和发送。两个模块在同一个服务进程中，拆成不同类不等于拆成不同进程。

```text
聊天连接：客户端 → ChatService::mediaRequest → MediaService::request
文件连接：客户端 → Nginx → MediaService::serve → upload / download
```

普通文件通路 `kind="file"` 按二进制字节处理，不需要理解 MP4、H.264、帧或音轨；当前 MP4 限制主要属于 Qt 聊天发送和播放入口。媒体服务仍检查权限、长度、摘要并保存资源状态；图片资源另有图片校验和缩略图处理，不能将整个 MediaService 理解为完全不区分资源类型的字节转发器。

### 直连与服务器内部转发

客户端和服务端分别运行。客户端连接公网聊天端口 `7000`，文件请求访问 `http://39.105.18.142/media`；服务器 Nginx 接收请求后转发到内部文件端口 `127.0.0.1:6002`。这里的 `127.0.0.1` 属于服务器，客户端无需建立本地隧道。

Nginx 只负责转发 HTTP，不替代登录会话和 Bearer 授权检查。上传和下载关闭代理整文件缓冲，继续分块流转；最大请求体与服务端的 100 MiB 上限一致。公网地址属于部署配置，不改变上传、发布、下载的业务协议。

当前学习环境明确采用 HTTP，文件及授权凭证没有传输加密。客户端仅对明确配置的文件地址允许公网 HTTP，不自动放开任意 HTTP 地址。

## 2. 上传、就绪、发布是不同动作

```text
选择 MP4
→ 分块计算 SHA-256
→ begin_file：声明会话、文件名、长度、摘要，申请 media_id 和上传凭证
→ HTTP PUT：QFile 提供原始文件字节
→ status：确认服务端状态为 ready
→ publish：用 media_id 形成正式聊天消息
→ 接收端收到实时通知，或者以后从历史记录读取
```

上传完成表示文件已经存在且校验通过；发布完成才表示它进入某个聊天会话。这样不会把尚未传完的文件展示成可播放消息。

`MediaTransfer::beginUpload()` 先通过聊天连接发送 `begin_file`，还没有传文件内容。应答返回资源编号及 `upload` 描述后，才调用 `upload()` 发起 HTTP PUT；如果同一发送任务对应的资源已是 `ready`，则直接进入发布，不重复上传。

- `request_id`：每次控制请求的编号，关联请求和应答。
- `client_msg_id`：一次发送意图的编号，上传申请和发布共同使用，供服务端防止重复发布。
- `media_id`：服务端保存的资源编号。
- `message_id`：正式聊天记录编号，用于消息去重和历史分页。

取消通过递增本地任务编号让迟到回调失效，并终止 HTTP 请求。资源已经分配但尚未发布时，可以请求服务端取消；发布阶段不提供取消，避免把“已经发出”误显示为“没有发送”。发布应答超时可能意味着结果未知，可重新打开会话核对历史。

`generation` 是客户端内部保存的任务代次，回调捕获它并与当前 `generation_` 比较；它不是服务端资源编号。申请上传的应答在取消后才到达时，客户端不会继续上传，而会尝试取消刚分配的资源。

## 3. 下载到播放的边界

```text
点击“下载并播放”
→ read：按会话和 media_id 申请原文件读取权限
→ 检查本地缓存：长度与 SHA-256 均匹配时直接 fileReady
→ 缓存缺失或损坏时 HTTP GET
→ readyRead：每次最多读取 64 KiB，写临时文件并累计 SHA-256
→ finished：检查 HTTP 状态、总字节数、SHA-256
→ QSaveFile::commit：确认完整文件
→ fileReady(本地路径)
→ MediaWindow::OpenFile
→ 第五阶段的解封装、声画解码、音频输出与视频显示
```

`readyRead` 只表示当前有数据可读，不能据此认为整个文件下载完成。`finished` 也可能是失败或取消，必须检查结果。摘要校验用于确认下载内容与服务端记录一致，不替代授权验证。

缓存是已完整校验的视频副本，位于系统缓存目录的 `ChatClient/videos`，使用 SHA-256 命名，退出程序后保留。同样内容可复用同一文件，不需要在内存里记住上次下载路径。文件存在不等于内容正确，因此播放前检查长度和摘要；缓存校验也按块执行，避免阻塞 GUI。权限检查仍通过 `read` 完成，缓存不会绕过服务器授权。

Windows 本机目录为 `C:/Users/lds/AppData/Local/cache/ChatClient/videos`。缓存缺失或损坏时下载到 `QSaveFile` 的临时文件，通过校验后才提交目标文件。播放器的 seek 此时只操作本地文件；没有断点续传，也没有实现“文件尚未收完就起播”。

## 4. 模块与关键 Qt API

| 对象或 API | 职责与数据归属 |
|---|---|
| `MainWindow` / `media_chat.cpp` | 聊天入口、文件消息、历史加载、播放器窗口生命周期 |
| `MediaTransfer` | 控制请求回调、上传下载、取消、长度和摘要检查 |
| `QNetworkAccessManager` | 在所属线程发异步 HTTP 请求；这里属于 GUI 线程，无须为网络另开线程 |
| `put(request, QFile*)` | 从文件逐步读取上传；QFile 必须活到请求结束，不能是提前析构的局部对象 |
| `QNetworkReply` | 一次 HTTP 响应及其接收缓冲；通过信号获取数据、进度、完成情况，结束后 `deleteLater()` |
| `setReadBufferSize(64 KiB)` | 限制该响应的 Qt 读取缓冲；配合分块落盘，避免整文件常驻内存，不表示整个进程只占 64 KiB |
| `QCryptographicHash::addData` | 逐块更新 SHA-256，不必把整文件合并成一个 QByteArray |
| `QSaveFile` | 下载过程写临时文件；校验成功才 commit，失败不会留下看似完整的目标文件 |
| `QStandardPaths::writableLocation(GenericCacheLocation)` | 获取系统通用缓存根目录，再拼接应用专属目录；不会自动删除文件 |
| `QProgressDialog::reset()` | 重置进度与内部计时；启用 `autoClose` 时同时隐藏窗口 |
| `MediaWindow` | 位于 Qt 客户端的 `player` 目录，负责播放窗口与调度；解码在后台线程执行 |

上传前的摘要计算也按块执行，每处理一块通过 `QTimer::singleShot(0, ...)` 让出事件循环，避免一次长循环阻塞窗口。

`network_.put(request, source_.get())` 发起异步上传，返回用于观察这次请求的 `QNetworkReply`，不会等待整份文件上传完成。Qt 从仍然有效的 QFile 逐步读取；`uploadProgress(done, total)` 报告发送进度，`finished` 表示请求结束，不保证成功。客户端还需检查网络错误、HTTP 状态码和响应 JSON 的 `ok`，再通过 `status` 确认资源可发布。`reply->readAll()` 读取的是服务端应答体，不是刚上传的视频。

文件任务包含摘要计算、上传、确认和发布等阶段。某一阶段进度达到 100% 不代表整个任务完成，因此进度窗口设置 `autoReset=false`；由业务 `finished` 统一调用 `reset()`，配合 `autoClose=true` 隐藏窗口。`finished` 表示任务退出，成功、失败、取消都需要恢复按钮；失败原因另由 `failed` 通知。

## 5. 聊天协议与异步状态

- `msgid = 26`：客户端控制请求，由 `op` 区分 `begin_file`、`status`、`publish`、`read`、`history`、`cancel`。
- `msgid = 27`：服务端应答。`request_id` 找到对应回调，`ok` 和 `error` 表示业务结果。
- `msgid = 28`：正式消息的实时推送。发送方使用发布应答显示自己的消息；接收方使用推送显示消息。

文件业务是“空闲 → 算摘要/申请/传输/校验/发布 → 空闲”，与播放器的 `Buffering/Playing/Paused` 是两套状态。传输完成不等于播放完成。

开始传输时保存会话 ID，之后切换联系人不会改变该文件的发送目标。历史查询也带本地编号，切换会话后忽略旧结果；当前会话的历史加载期间暂存实时文件消息，加载完成后追加并按 `message_id` 去重。

## 6. 服务端控制入口、身份与上传凭证

### ChatService::mediaRequest 检查什么

```text
接收 msgid 26 → actor(session) 确认登录用户
    → 检查 request_id → co_await MediaService::request
    → 成功结果放入 data，失败原因放入 error → 返回 msgid 27
```

`session` 是发来控制请求的聊天 TCP 连接。登录成功后，服务端记录“连接 → 用户 ID”；`actor(session)` 查询这份关系，返回 0 表示没有有效登录身份。这里不重新验证密码，也不相信客户端自行声明的发送者 ID。

入口直接检查 `request_id` 是否存在、是否为字符串、是否非空且不超过 64 字节。`media_service_` 的检查只表示服务对象是否可用。`op`、会话、资源编号、文件长度和摘要等具体业务参数，由 MediaService 与 MediaRepository 继续检查。确认“你是谁”与确认“你是否有权向该会话发送或读取该资源”是两层判断。

协议使用的是整数编号，枚举只是源码中的名称。当前服务端 `chatservice.cpp` 直接使用 26、27、28，即使 `public.hpp` 未列出它们，已注册的处理逻辑仍然有效；Qt 客户端用 MediaRequest、MediaResponse、MediaMessage 命名同一组编号。

### descriptor 如何发放凭证

申请成功后，`MediaService::descriptor(Ticket ticket)` 生成随机 token，在服务端保存授权信息，向客户端返回传输描述：

```text
method：PUT（上传）或 GET（下载）
url：当前部署为 http://39.105.18.142/media
headers.Authorization：Bearer <随机 token>
expires_at：凭证过期时间
```

```cpp
const auto token = Random(32);
tickets_.emplace(token, std::move(ticket));
```

`Random(32)` 使用随机字节生成十六进制字符串；`tickets_` 是服务进程内的 `token → Ticket` 映射。客户端持有字符串凭证，具体权限由服务端保存，不是从 token 文本中直接解析用户和文件信息。

| Ticket 成员 | 含义 |
|---|---|
| `actor` | 获得授权的用户 ID |
| `session` | 关联的聊天登录连接，使用 weak_ptr；不是本次 HTTP socket |
| `conversation` | 读取资源所属的会话，用于下载权限检查 |
| `media_id` | 本次允许操作的资源编号 |
| `variant` | 原文件 original 或缩略图 thumbnail |
| `upload` | 是否允许上传，决定使用 PUT 还是 GET |
| `deadline` | 用单调时钟判断的授权截止时间 |

上传地址通常固定，凭证按任务申请。当前凭证有效期约五分钟，服务端在接收 HTTP 请求时检查它；上传过程另有超时控制，不能把凭证有效期当作整个文件必须传完的时长。

### HTTP 请求如何使用凭证

`serve()` 从 Authorization 取出 `Bearer ` 后面的 token，查找 tickets_，检查是否存在、是否过期、关联聊天连接是否仍有效且登录用户一致，以及请求方法是否匹配。随后查询数据库核对资源归属、状态等业务条件。

上传凭证通过凭证、登录连接和方法检查后就从 tickets_ 删除，属于一次性使用；删除发生在文件收完之前，上传失败不能假定原凭证仍可重用。下载凭证在有效期内仍需接受相应权限检查。知道服务器地址或 media_id，都不能替代有效凭证。

## 7. 服务端怎样接收 HTTP 文件并写入磁盘

### 从接受连接到进入上传协程

```text
MediaService::start
    → 启动 accept 协程
acceptor_.async_accept
    → 得到 TCP socket，为该连接启动 serve 协程
serve
    → beast::tcp_stream 管理 socket
    → async_read_header 读取并解析 HTTP 请求头
    → 检查路径、凭证、方法、资源状态、Content-Length
    → co_await upload(stream, buffer, parser, ticket, media)
```

当前通过 Nginx 转发，文件服务 socket 的直接对端是服务器上的 Nginx。`async_accept()` 接受的是通信连接，不等于已经读完请求；连接建立后，由 Beast 在 TCP 字节流上解析 HTTP。

一次上传通常是一个 PUT 请求，请求头描述方法、授权和长度，请求体是整个文件。后续循环读取同一个请求体，不会每收一块就建立连接、解析一份新请求头；字节仍不断经过客户端、Nginx 和后端连接。

### 读取缓冲与写入缓冲

| 对象或 API | 作用 |
|---|---|
| `beast::flat_buffer buffer` | 暂存网络读取但尚未被 HTTP 解析器消费的字节；读请求头时顺带读到的请求体也不会丢失 |
| `http::request_parser<http::buffer_body>` | 解析 HTTP 结构，把请求体交给应用提供的内存 |
| `async_read_header` | 读到完整请求头，使方法、路径、请求头字段可用 |
| `async_read_some` | 增量推进读取与解析，不保证一次读满应用缓冲 |
| `parser.is_done()` | 当前 HTTP 消息是否已经完整解析 |
| `DiskUpload::Append` | 将本轮取得的文件字节追加写入上传文件 |

核心循环的缓冲用法：

```cpp
parser.get().body().data = bytes.data();
parser.get().body().size = bytes.size();
co_await http::async_read_some(stream, buffer, parser,
    asio::redirect_error(asio::use_awaitable, ec));
const auto count = bytes.size() - parser.get().body().size;
```

读取前，`body().size` 是可用容量；读取后，它是剩余容量，所以相减得到实际写入 bytes 的文件字节数。bytes 的容量为 64 KiB，不是 TCP 包大小，也不保证每次装满。buffer_body 用完本轮空间时可能报告 `http::error::need_buffer`，代码允许这一结果，处理本轮数据后重新提供缓冲；其他读取错误会转成异常。

每轮按 count 更新 SHA-256，并通过 `co_spawn(workers_, ...)` 将 `Append` 交给工作线程池，等待该块写完后再复用 bytes。不是把整个文件接收进内存后一次写盘。

本例要求 Content-Length 与申请时声明的文件长度一致。解析器据此判断请求体结束，不依赖客户端断开连接；文件收齐后检查摘要，提交文件，更新资源状态为 ready，然后 serve 返回 HTTP 200 和 `{"ok":true}`。Qt 的 finished 回调再检查这个结果。普通文件通路不会在此解码音视频，图片通路还包含图片处理。

## 8. 发布、数据库记录与实时推送

### 文件资源与聊天记录分开保存

| 存储位置 | 保存内容 |
|---|---|
| `Media` 表 | 资源编号、所有者、文件名、长度、摘要、存储键、资源状态等 |
| `History` 表 | 发送者、会话、消息类型、media_id、client_msg_id 等聊天记录信息 |
| 服务器磁盘 | 视频文件本身的二进制内容 |

`History.media_id` 关联 Media。上传文件得到 ready 资源后，尚不等于会话已有一条消息；`MediaRepository::publish()` 检查权限、资源归属和会话一致性，并在事务中写入 History。文件消息的 kind 为 file，查询历史时将资源信息组合进消息返回。

相同 client_msg_id 的发布若已经成功，则返回既有消息并设置 `created=false`；首次创建返回 `created=true`。它避免同一次发送因重试而形成多条聊天记录，不表示仅凭相同文件摘要就能跳过所有业务检查。

### msgid 28 推送的是什么

发布成功后，ChatService 先用 msgid 27 回复请求方；只有 publish 或 send_text 成功且 created 为 true 时，才推送 msgid 28。推送内容包括会话、发送者、消息编号和媒体描述，例如 media_id、文件名、大小，不包括视频字节。

接收方根据通知生成视频卡片，点击后才申请读取并检查本地缓存，必要时通过 HTTP 下载。因此，“收到视频消息”与“视频已经下载”是两个不同状态。私聊通知中的 conversation.target 是发送者 ID，群聊则仍为群 ID，这是接收方识别会话的依据。

### 业务 publish 与 Redis publish

```text
客户端 MediaTransfer::publish
    → op="publish" → MediaRepository::publish 保存聊天消息
    → ChatService 通知接收方
        ├─ 连接在当前进程：通过 Session 直接发送
        └─ 当前进程没有连接：Redis publish 广播给订阅进程，并更新未读计数
```

业务 publish 完成的是消息入库；Redis publish 完成的是进程之间的通知传播。Redis Pub/Sub 本身不会创建聊天记录，也不保存视频文件，订阅者未收到通知时不能依靠 Pub/Sub 取回历史；历史来自数据库。当前进程没有用户连接，不一定意味着用户在所有服务进程上都离线。

实时通知发生在消息提交之后。通知失败时记录日志，不把已提交的消息当作未发送；客户端可通过历史查询找回。

## 9. 上传失败后的清理与异常传播

`upload()` 捕获上传中的异常，用 `std::current_exception()` 保存为 exception_ptr，随后尝试删除当前资源文件，并调用 `repository.fail(..., "upload_failed")`。数据库更新的是 `state='failed'` 和失败原因，不是用户主动取消的 canceled 状态。

```text
serve：co_await upload(...)
    → upload 出错，保存原异常
    → 尝试清理文件、更新失败状态
    → std::rethrow_exception(failure)
    → 异常回到 serve 的 co_await 位置
    → serve 的 MediaError / ImageError / std::exception 处理器捕获
    → 尝试返回 HTTP 错误应答，关闭当前连接，结束本次协程
```

`rethrow_exception` 保留原异常类型并继续向外传播，本身不意味着结束进程。上述上传错误由 serve 处理；其他连接与监听协程仍可以继续工作。连接已经断开时，错误应答可能无法送达。

清理是尽力执行，不是保证完成：删除或数据库操作可能再次失败，内部 `catch (...) {}` 会忽略清理异常；数据库连接不可用时也可能跳过状态更新。进程崩溃或被强制结束，不能保证执行到 catch。不能把这段逻辑理解为“任何中断都能完整回滚”，也不能把磁盘文件与数据库状态视为一个原子事务。
