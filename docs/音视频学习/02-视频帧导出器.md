# 第二阶段：解码帧、像素与图像转换

## 1. 容器、编码、像素格式与帧类型

| 概念 | 描述什么 | 例子 |
|---|---|---|
| 容器格式 | 怎样组织轨道、编码数据、时间戳等信息 | MP4、Matroska |
| 编码格式 | 图像怎样被压缩，以及怎样还原 | H.264、H.265、VP9 |
| 像素格式 | 解码后的分量、位深、采样方式和内存排列 | RGB24、YUV444P、YUV420P |
| 图像编码类型 | 编码一幅图时采用的预测依赖类型 | I、P、B |

```text
MP4 容器中的视频轨道
    └─ H.264 编码数据：AVPacket
           └─ 解码后的图像：AVFrame，例如 YUV444P
                  └─ 像素转换后的图像：AVFrame，例如 RGB24
```

这些概念不是一一对应的：MP4 可以容纳不同编码；H.264 可以解码出不同像素格式；I/P/B 都可以还原成完整像素图像。解码完成后，`pict_type` 仍可记录图像原来的编码类型，但像素数据已不是预测指令或残差。

更换 H.265、VP9 等解码器时，`AVPacket`、`AVFrame` 和送包/取帧接口仍可沿用；输出像素格式、位深和颜色属性可能变化，必须读取实际帧信息。硬件解码帧还可能位于设备内存，不能默认直接按 CPU 字节访问。

### H.264：编码配置与实际画面数据

H.264 也叫 AVC，是视频编码标准。它规定图像怎样压缩、编码数据怎样解释和重建，不规定使用 MP4、FLV 还是网络传输。

实际的编码画面数据包含预测方式、运动信息、量化后的残差等，解码后才成为像素；它不是 RGB/YUV 像素数组。除此以外，解码器还需要编码配置，知道按什么参数解释这些内容。

```text
编码配置：说明怎样解释画面数据
                 ↓
编码画面数据 → H.264 解码器 → 完整像素图像
```

### NAL、SPS、PPS 与 slice

H.264 编码数据组织为 NAL 单元。NAL 是有类型的编码数据单元，不等于一幅画面，也不等于 AVPacket 或 TCP 包；名称中的 Network Abstraction Layer 不表示它只用于网络，文件中也保存这种结构。

| 内容 | 作用 |
|---|---|
| SPS：Sequence Parameter Set，序列参数集 | 保存一组图像使用的整体编码参数，如 profile、level、尺寸相关信息和参考图像约束等 |
| PPS：Picture Parameter Set，图像参数集 | 保存解码图像切片使用的参数，如熵编码方式、量化相关设置等；它引用一个 SPS |
| 编码 slice：图像切片 | 描述一部分画面怎样重建，包含切片头和压缩后的图像信息；切片头引用一个 PPS |

SPS/PPS 本身也是 NAL 单元。一幅编码画面可以由多个 slice 组成，也就可能包含多个 NAL 单元。解码器通过切片里的 PPS 标识找到 PPS，再找到其引用的 SPS，不需要每个切片都重新携带一整份配置。

```text
SPS：定义整体编码条件
  ↑ PPS 引用
PPS：定义切片使用的参数
  ↑ slice 引用
IDR 或其他图像的 slice：描述实际画面
```

IDR 图像可以提供不依赖之前参考画面的起播点，但仍需要有效的 SPS/PPS。I/P/B 描述图像的预测类型，不能用来表示“是否已经取得编码配置”；并非所有 I 图像都具有 IDR 的解码刷新语义。编码参数可以变化，解码器需要取得后续图像实际引用的有效参数。

### 参数集在文件中怎样保存

在 MP4 中，H.264 初始化信息通常保存在视频轨道的 avcC 配置记录中。其结构称为 `AVCDecoderConfigurationRecord`，通常包含 profile、level、NAL 长度字段宽度和 SPS/PPS。它不是一张待显示的图像。

```text
MP4 轨道配置：AVCDecoderConfigurationRecord（含 SPS/PPS 等）
MP4 编码样本：[NAL 长度][NAL 内容][NAL 长度][NAL 内容]……
```

NAL 长度不固定，配置记录说明长度字段本身占几个字节。另一种常见组织方式是 Annex B，用起始码（如 `00 00 01`）分隔 NAL。长度前缀与起始码是组织编码数据的方式，不是两种视频压缩算法。NAL、画面、容器样本和 FFmpeg 编码包不是同一个层次，不能假定一一对应。

FFmpeg 解封装后，用 `AVCodecParameters::extradata` 保存取得的初始化信息；当前 MP4/H.264 输入通常包含 AVC 配置记录。初始化解码器时：

```text
流的 codecpar（包括 extradata）
  → avcodec_parameters_to_context()
  → avcodec_open2() 初始化解码器

av_read_frame() 读取实际编码包
  → avcodec_send_packet() 提交编码内容
  → avcodec_receive_frame() 接收像素图像
```

配置说明“如何解码”，编码包承载“要解码的画面”。同样的 H.264 可以用于本地点播或直播，不同容器和传输协议只是采用不同方式携带这些内容。

## 2. 像素在内存中的表示

### RGB24：每个像素三个字节

RGB 用红、绿、蓝三个分量表示颜色。RGB24 的每个分量占 8 位，即一个字节，数值范围为 0～255；一个像素合计 24 位、3 字节。

```text
红色像素：255, 0, 0
绿色像素：0, 255, 0
白色像素：255, 255, 255

一行两个像素（红、绿）：
内存字节：255 0 0 | 0 255 0
```

RGB24 将 R/G/B 交错存放在同一个平面，通常由 `data[0]` 访问；每行有效数据为 `width × 3` 字节。

位深指每个分量的位数。8 位有 256 个数值等级，10 位有 1024 个等级；10 位分量在某些格式中用 16 位空间存储，不能直接用“宽度 × 位深”推断实际行跨度。

### YUV：亮度与色度分开表示

数字视频中常说的 YUV 通常指 Y′CbCr：Y′ 表示亮度相关信息，Cb、Cr 表示蓝、红方向的色差信息，习惯上也称 U、V。它们共同描述颜色，不是 RGB 三个分量，需要按相应矩阵和数值范围转换。

以下是 8 位平面格式，`P` 表示 planar，即各分量分开存储：

| 像素格式 | Y 平面 | U、V 平面 | 含义 |
|---|---|---|---|
| YUV444P | 宽 W、高 H | 各为 W × H | 每个像素位置都有对应的三个分量样本 |
| YUV420P | 宽 W、高 H | 各为 ceil(W/2) × ceil(H/2) | 色度在水平、垂直方向都减少采样 |

例如一张 4×4 的 YUV420P 图像，Y 有 16 个样本，U、V 各有 4 个样本。减少的是色度采样数量，不是把整张图缩成 2×2；恢复 RGB 时需要重建每个像素位置的色度。

```text
YUV444P / YUV420P：
data[0] → Y 平面
data[1] → U 平面
data[2] → V 平面
```

平面是同一张图的组成部分。不是所有像素格式都使用三个平面，也不是所有平面都与图像宽高相同。

### 行跨度 linesize

`linesize[i]` 表示第 i 个平面中，相邻两行起点的距离，单位为字节。有效像素后可能有对齐填充，因此行跨度不一定等于有效字节数。

```text
样本的 YUV444P：宽度 1820，某平面 linesize 为 1856
一行：[1820 字节有效分量][36 字节填充]
下一行起点：向后移动 1856 字节
```

第 y 行起点为 `data[i] + y × linesize[i]`。一般情况下行跨度也可能为负。写出连续像素文件时，应逐行写有效字节，不把内存填充写进去。

## 3. AVFrame：像素引用与描述信息

`AVFrame` 是 C 结构体。视频帧既包含像素缓冲区的引用，也包含尺寸、格式、时间和颜色信息；像素并非整个内嵌在结构体中。音频也使用 AVFrame，但这里讨论视频。

| 成员 | 含义 |
|---|---|
| `width`、`height` | 图像宽高，单位为像素 |
| `format` | 类型为 int；视频中存放 `AVPixelFormat` 枚举值 |
| `data[i]` | 第 i 个数据平面的访问指针，解释方式由像素格式决定 |
| `linesize[i]` | 第 i 个平面的行跨度，单位为字节 |
| `pts` | 帧的呈现时间戳 |
| `best_effort_timestamp` | FFmpeg 根据可用时间信息推断的呈现时间戳 |
| `pict_type` | I/P/B 等图像编码类型 |
| `color_range`、`colorspace`、`color_primaries`、`color_trc` | 像素数值的色彩解释，见下一节 |

本例设置 `context->pkt_timebase = stream->time_base`，输出的帧呈现时间按该流时间基解释：`秒数 = 时间戳 × time_base.num / time_base.den`。未知时间戳为 `AV_NOPTS_VALUE`，不能当普通数值换算。

当前输出帧不一定对应刚送入的包，必须使用帧自身的时间信息。例如送入 PTS 为 0.25 秒的包后，可能才输出 PTS 为 0 秒的帧。解码器管理依赖和输出重排，应用不应先把编码包按 PTS 排序。

`av_get_pix_fmt_name()` 只把格式编号转换成名称，例如 `AV_PIX_FMT_RGB24 → "rgb24"`；`av_get_picture_type_char()` 将图像类型转换成 I/P/B 等字符。二者都不转换像素。

日志中的 `frame index`、`phase` 是程序自己的计数和阶段标记；`stream` 来自所选 AVStream，它们不是 AVFrame 的这些成员。

## 4. 像素格式与色彩属性

像素格式回答“字节怎样排列”，色彩属性回答“这些数值代表什么颜色”。只有 RGB24 这一信息，不足以确定完整的颜色含义。

| 属性 | 作用 | 例子或区别 |
|---|---|---|
| `color_range` | 规定正常数值范围 | 8 位完整范围为 0～255；常见有限范围 YUV 的 Y 为 16～235、U/V 为 16～240 |
| `colorspace` | 说明颜色分量表示及 YUV/RGB 转换矩阵 | BT.709 矩阵；`AVCOL_SPC_RGB` 表示 RGB 分量表示 |
| `color_primaries` | 定义 RGB 基色及白点，关系到色域 | BT.709 与 BT.2020 的基色定义不同 |
| `color_trc` | 定义编码分量数值与光强之间的传递关系 | 通常非线性，数值 128 不必然对应 255 的一半光强 |

`AVCOL_RANGE_JPEG` 表示完整数值范围，不表示正在编码 JPEG 图片。范围或矩阵解释错误，可能导致黑色发灰、亮部或颜色失真。`colorspace` 不是包办所有色彩属性的总开关。

目标帧设置 RGB24、原宽高、完整范围与 RGB 表示，并复制源的基色和传递特性，表示保留这些色彩含义。赋值本身只设置描述信息，像素计算由转换函数完成；源属性未知时，复制也不会让它变成已知。

RGB24 不自动等于 sRGB，复制色彩属性也不等于完成 HDR 到 SDR 的色调映射。

## 5. 解码与转换对象的关系

| 对象 | 保存什么、负责什么 |
|---|---|
| `AVCodecParameters` | 流的编码参数，如 codec_id、宽高、编码初始化数据 extradata |
| `AVCodec` | 库提供的编码器或解码器实现描述；本例使用解码器，不由调用方释放 |
| `AVCodecContext` | 一次编解码的工作实例；本例保存解码配置、参考图像和缓存等状态 |
| `AVPacket` | 编码数据及包的时间戳、流编号等信息 |
| `AVFrame` | 解码后的图像或转换后的图像，以及相应描述信息 |
| `SwsContext` | libswscale 的图像转换上下文，保存转换配置、工作状态和缓存 |

同一条流的包持续送给同一个 `AVCodecContext`，才能保留参考图像等状态。通常每条需要解码的音视频流各建一个实例；两条同为 H.264 的视频流也需要独立实例，但可以使用同一个 AVCodec 实现描述。不解码的流不需要实例。

```text
AVCodecParameters → 提供参数 → AVCodecContext
AVCodec           → 提供实现 → AVCodecContext
AVPacket          → 解码    → AVFrame（源像素）
AVFrame（源像素）  → 转换    → AVFrame（目标像素）
                              转换由 SwsContext 参与完成
```

### 主要 API 的职责

| API 或配置 | 含义 |
|---|---|
| `avcodec_find_decoder(codec_id)` | 按编码编号查找解码实现；找不到返回空指针 |
| `avcodec_alloc_context3(codec)` | 分配上下文、设置默认值；尚未完成解码器初始化 |
| `avcodec_parameters_to_context()` | 将流参数复制到上下文，包括所需的编码初始化数据；不读取编码包 |
| `context->pkt_timebase` | 声明输入包的时间戳单位，不改写包的时间戳数值 |
| `context->thread_count` | 解码线程配置；设置为 1 不会消除 B 帧重排序延迟 |
| `avcodec_open2()` | 根据配置初始化解码器；第三个参数为可选选项字典，nullptr 表示不额外提供 |
| `avcodec_send_packet()` | 提交编码包，成功表示包已被接受，不保证立即输出一帧 |
| `avcodec_receive_frame()` | 取得一帧输出；返回 0 后，输出 AVFrame 中才有本次结果 |
| `sws_alloc_context()` | 创建像素转换上下文 |
| `sws_scale_frame(context, dst, src)` | 依据源帧和目标帧的尺寸、格式、颜色属性转换像素 |

MP4/H.264 的 extradata 通常携带 SPS、PPS 等参数，帮助解码器解释后续编码数据；它不是一张待显示的图像。

`SwsContext` 处理已解码的像素，可做像素格式转换、缩放及颜色转换，不负责解码 H.264。当前使用 FFmpeg 8.1.1 的动态帧转换接口：设置目标 AVFrame 的规格后，`sws_scale_frame()` 可以为尚无像素缓冲的目标分配空间并写入结果；源、目标宽高相同则不改变图像尺寸。

## 6. 输入、输出与缓存

送包与取帧不是一一对应的调用：一次送包后可能暂时没有帧，也可能有多个输出。多个包之后才输出一帧，不一定意味着图像被物理拆在几个包里，也可能是等待参考图像或输出重排。不能把任意截断的编码字节直接当作完整 AVPacket。

send/receive 是同步调用，接口分离不要求使用两个线程。

| 状态 | 含义与处理 |
|---|---|
| send 返回 0 | 包已接受，可释放调用方的包数据引用，并接收输出 |
| send 返回 `AVERROR(EAGAIN)` | 包尚未接受，先接收输出，再重送同一个包 |
| receive 返回 0 | 得到一帧，处理后继续取当前可用的帧 |
| receive 返回 `AVERROR(EAGAIN)` | 当前需要更多输入，结束本轮取帧 |
| `av_read_frame()` 返回 EOF | 输入读完，解码器可能仍有缓存帧 |
| 成功 send 一个 nullptr | 提交输入结束信号，进入排空状态 |
| 排空时 receive 返回 `AVERROR_EOF` | 缓存结果已全部取完 |

EAGAIN 是输入输出状态，等待时间本身不能让它恢复。其他负数错误应另行检查。排空是取出剩余结果；`avcodec_flush_buffers()` 是重置解码状态，不能代替文件结束时的排空。

## 7. 对象、缓冲区与所有权

`context_` 管理解码实例，`frame_` 是反复接收输出的帧对象。帧对象持续存在，不代表每次收到的都是同一张图。

```cpp
using FramePtr = std::unique_ptr<AVFrame, void (*)(AVFrame*)>;
```

`FramePtr` 是 C++ 类型别名，不是 FFmpeg 类型：它独占管理一个 AVFrame，第二个模板参数规定删除器为函数指针。`get()` 借用原始指针，`->` 访问成员，销毁时自动调用删除器。

| 操作 | 对象和数据的变化 |
|---|---|
| `av_frame_alloc()` | 创建并初始化帧对象；尚无一张视频图像的像素缓冲 |
| `avcodec_receive_frame()` 成功 | 填入输出帧信息及像素缓冲区引用 |
| `av_frame_unref()` | 释放当前数据引用并重置字段，保留帧对象 |
| `av_frame_free(&frame)` | 释放数据引用和帧对象，并将传入的指针置空 |
| `av_packet_unref()` | 释放当前包数据引用，保留包对象 |
| `avcodec_free_context()` | 释放解码上下文及其持有的资源 |
| `sws_free_context()` | 释放转换上下文 |

`CreateFrame()` 调用 av_frame_alloc，将结果交给带删除器的 FramePtr，失败时抛出异常；返回时转移所有权，不复制图像。无捕获 lambda 可转换成删除器所需的函数指针，内部调用 `av_frame_free(&value)`；这里传地址是因为释放 API 接收二级指针。

帧被 unref 或复用后，不能继续使用之前借用的像素指针。若其他对象持有同一缓冲区的有效引用，缓冲区可继续存在，释放一个引用不等于必然立即释放整块内存。

## 8. 从像素到图片文件

RGB24 是内存中的像素格式，PPM/PNG/JPEG 是图片文件格式。拿到 RGB 字节并不等于已经生成某种图片文件，还需要按文件格式组织或编码。

PPM 的 P6 形式可以直接保存 8 位 RGB：三行头部为 `P6`、`宽 高`、`255`，后面紧接逐行排列的 RGB 字节。`255` 为分量最大值；不写行对齐填充，也不压缩像素。1820×1030 的 RGB 像素数据共有 5623800 字节。这个简单 PPM 文件不携带上述完整色彩标签。

`SaveFirstFrame()` 设置目标帧规格，使用 SwsContext 将源像素转换成 RGB24，再写 PPM。只保存第一张图片是程序的输出选择，不表示只解码第一帧；后续帧仍可继续解码、统计或用于显示。
