## 小项目与阶段验收

各阶段的实现任务由 Codex 完成并讲解，tianmu_sama 主要阅读、提问和观察现象，可自愿修改参数做实验。功能验收和知识理解分别确认，不把实现完成等同于用户已经掌握。

### 1 媒体信息查看器

先理解容器、编码、流、编码包和解码帧；结合样本讲帧率、码率、PTS、DTS 与时间基。视频压缩先建立帧内预测、帧间预测、I/P/B 帧与 GOP 的直觉，具体算法随实验深入。

任务：先读 `ffprobe` 输出，再用 `avformat_open_input`、`avformat_find_stream_info`、`av_read_frame` 打印流信息和前若干个包。解释时间戳如何换算为秒，以及为什么编码包不能直接作为图片显示。

验收：输出能与 ffprobe 对上；无音轨被正常识别；文件打不开有明确错误；能区分读取顺序与显示顺序。

### 2 视频帧导出器

学习解码器的输入输出关系、AVPacket/AVFrame 的生命周期、YUV/RGB、平面与行跨度。任务先只导出一帧，再遍历全文件并统计帧数。

使用 send/receive 解码流程，正确处理 EAGAIN 和 EOF 排空；用 libswscale 转换像素。不要把一次输入必然对应一次输出写进循环假设。[FFmpeg 编解码 API](https://ffmpeg.org/doxygen/8.1/group__lavc__encdec.html)

验收：原样本完整解出 40 帧；导出的图像方向、颜色、尺寸正确；无损坏行或失效内存引用。通过改变输入像素格式观察代码是否仍然正确。

### 3 无声视频播放器

把帧导出器接到 Qt 窗口。先通过 QImage 显示，再加入后台解码、最多一张待显示帧和按 PTS 调度的显示过程。无音频时用单调时钟作为播放参考。多帧队列扩展安排在服务端流媒体学习完成之后。

验收：5 秒视频按约 5 秒时间尺度播放；GUI 保持响应；暂停期间时钟处理正确；关闭窗口能停止工作线程；待显示图像不会无限积压。此阶段先弄清数据所有权和线程分工。

### 4 音频播放实验

先将带音轨文件解码，并用 libswresample 转换成统一格式的 PCM，保存为文件以观察采样数据。知识笔记先讲清采样率、声道、样本格式、平面与交错布局、音频 AVFrame 和 API 调用关系，再补充向设备提交 PCM 及设备缓冲。当前独立示例为 `lessons/audio_decode`，测试音轨已加入原视频的副本，保留原无音轨文件作为对照。

使用实际 Qt 版本对应的音频接口：Qt 5 的 QAudioOutput 或 Qt 6 的 QAudioSink。先检查设备支持的格式，不把解码器输出格式直接当作设备输入格式。Qt 6 接口职责见 [QAudioSink 文档](https://doc.qt.io/qt-6/qaudiosink.html)，实现时查所选版本。

验收：声音速度和音高正常；暂停与停止行为正确；知道已解码、已提交设备、估计已播放的音频时长分别代表什么。

### 5 完整本地播放器

在第三阶段 Qt 无声播放器基础上接入第四阶段的音频解码与重采样。一个解封装上下文读取音视频包，按 stream_index 送入各自的解码上下文；音频 PCM 经格式转换送入 Qt 5 的 QAudioOutput，视频继续经 QImage 显示。设备格式协商、有限缓冲、部分写入和剩余 PCM 保留属于本阶段的新知识。

用音频播放进度作为参考安排视频；早到的画面等待，明显落后的画面按策略丢弃。估算时钟时考虑设备缓冲，不能只累计送入设备的样本数；声画采用共同媒体时间轴，保留原始起始偏移。无音轨时沿用单调时钟播放。

加入当前时间、总时长和进度条，支持点击位置跳转、拖动后松手跳转。seek 分成定位到可解码位置、清理待播放数据、avcodec_flush_buffers 清理解码状态、清空设备缓冲并重置重采样状态、解码到目标位置、重建时钟几个动作。定位可能落在更早的关键帧，需要丢弃目标前画面、按采样处理目标前音频；暂停时跳转保持暂停并更新目标画面，会话编号阻止旧结果进入新位置。

同阶段补充音量、静音、停止与重播、全屏/退出全屏，以及空格播放暂停、左右键短距离跳转。持续读取、暂停、缓冲、结束与停止分别处理，文件读完后还要等待设备中的尾音播放完毕。阶段入口为 lessons/video_player/build/media_player.exe，知识文档为 05-音画同步与进度跳转.md；队列性能扩展放在服务端流媒体学习完成后。

代表样本采用现成的 Sintel 预告片：lessons/video_player/samples/sintel_trailer.mp4，约 52.21 秒，H.264 480p/24 fps + AAC 48 kHz stereo；实际下载文件已用 ffprobe 确认参数。必要验证覆盖正常声画播放、暂停恢复、非关键帧位置跳转、切换文件和原无音轨样本；观察有无持续增长的漂移或旧声音、旧画面残留。该预告片不作为精确测量声画偏差的标记样本。

### 6 聊天中的视频文件

复用现有文件业务，先将视频作为普通文件上传和发布，在 Qt 增加发送、下载、打开播放的入口。服务端已有文件存储能力，第一轮不以增加 video 数据类型、服务端封面和转码任务系统为前提。

本阶段按 tianmu_sama 的直接实施要求，先提供可运行的 MP4 收发与播放接入，再逐项带读关键代码。Qt 客户端的 `MediaTransfer` 处理授权和文件传输，`media_chat.cpp` 连接消息界面和第五阶段播放器；知识笔记为 `06-聊天视频收发与播放.md`。第五阶段的队列扩展推迟到服务端流媒体内容学完之后。

学习并实现：通过聊天会话申请上传 → HTTP 上传 → 确认 ready → 发布 media_id → 接收方获得读取授权 → 下载到本地 → 调用播放器。小程序中的播放逻辑在接入点需要时整理，不预先设计大型播放器框架。

播放器接入时，Codex 完成适配与验证，并围绕解码循环、音画同步决策和 seek 状态清理逐项讲解。能直接复用的代码沿用，教学重点放在处理机制和项目接入差异上。

验收：两个账号收发成功；已发布文件可从历史访问；取消和失败有明确反馈；未授权账号拿到 media_id 也不能读取；普通文件的保存行为仍正确。之后可增补时长、尺寸、封面和视频消息展示。

### 7 HTTP 视频点播

已实现并部署：单段 Range、聊天视频在线/下载双入口、输入类型分离、网络缓冲与取消、凭证刷新；无设备时允许无声播放。知识记录在 `docs/音视频学习/07-HTTP视频点播.md`，构建部署与验证记录在 `docs/STAGE7_DELIVERY.md`。

服务端保留有界读写，在已有 GET 路径增加字节范围解析、定位和限制发送长度。先支持单段范围，明确普通 GET、合法范围、不可满足范围与不支持的多段范围的行为。核对 200、206、416、Content-Length、Content-Range 和 Accept-Ranges。[HTTP 范围请求规范](https://www.rfc-editor.org/rfc/rfc9110.html#section-14)

客户端先让 FFmpeg 打开 HTTP 地址，并传入现有描述中的 Authorization 请求头，复用本地解码与播放流程。网络读取放到后台，加入缓冲状态、超时、中断读取和取消。FFmpeg 已提供 HTTP 输入及自定义请求头选项。[FFmpeg HTTP 文档](https://ffmpeg.org/ffmpeg-protocols.html#http)

当前读取凭据有效期为五分钟，并关联登录会话；它在有效期内可重复用于读取。必须安排“暂停后凭据过期，再 seek”的实验，确定重新申请授权和恢复播放的处理。时间跳转由容器索引映射到字节位置，不能按总文件大小线性猜偏移。

验收：使用较长样本和限速记录首帧时刻、已传字节数、Range 请求及缓冲变化；证明确实在文件未收完时起播；拖动后读取目标区间；停止播放能中断等待；慢客户端的缓冲保持有界。尾部 moov 和 faststart 两个版本都要解释其请求差异。

## 后续服务端阶段

后续以三个工作层次组织学习：媒体处理（编解码、时间戳、打包）、媒体传输（接入、协议、分发）和服务管理（授权、任务、生命周期、资源与观测）。每阶段先讲数据和 API，再完整实现最小链路，最后接入已有聊天项目。不是只运行几条命令，也不要求自行重写全部成熟协议。

### 8 媒体处理与多清晰度 HLS 点播

只分两部分，每部分围绕一个完整成果学习，不再把每个知识点拆成独立课程。最终让同一个聊天视频保留原件下载，同时提供可鉴权访问的多清晰度 HLS。

#### 8.1 媒体处理：转封装与转码

已实现教学工具 `lessons/media_process`：MP4/MKV 转封装、480p/360p H.264 + AAC 转码，配套知识记录在 `08-媒体处理与HLS点播.md` 的 8.1 部分。已完成有声/无声样本、重采样、完整解码与 seek 的必要验证，构建与样本结果见工具 README。

用一个 C++ 小工具完成两种处理：直接复制编码包进行转封装；解码、缩放后重新编码，生成两档视频。先用现有样本做 480p/360p，保留原件，不引入额外业务模块。

结合这一个程序讲清：转封装与转码的区别，输入/输出上下文，分辨率、像素格式、码率、CRF/preset，GOP/IDR 与关键帧，以及 PTS/DTS、时间基转换和编码器排空。参数只选当前实验需要的几项，不逐个扩展成专题。

核心 API：`avformat_alloc_output_context2`、`avformat_new_stream`、`avcodec_parameters_copy`、`avformat_write_header`、`av_packet_rescale_ts`、`av_interleaved_write_frame`、`av_write_trailer`；转码加入 `avcodec_send_frame` / `avcodec_receive_packet` 和缩放、重采样。

成果与验证：转封装输出和两档转码输出均能播放、seek，尺寸和码率符合预期；对照文件大小与处理耗时，能说明哪些操作改变编码内容，哪些只改变容器组织。

#### 8.2 HLS 点播：分片、多清晰度与项目接入

已实现：客户端上传原件后，MySQL 持久任务驱动服务端 Linux `media_process hls` 生成并发布 TS/fMP4；C++ 服务端校验整套 HLS 凭证并分块发送，Qt 根据已就绪列表手动切档、保留进度和暂停意图。两份样本已做公网播放、定位、切档和客户端续签验证，细节见 `docs/STAGE8_DELIVERY.md`。ABR 另有基于实际分片大小的观察脚本，播放器尚未自动选档。

在前一部分媒体处理工具上，根据原视频分辨率选择输出档位，再打包成 HLS，提供主播放列表、子列表和分片，并接入现有聊天服务及 Qt 播放器。初始候选档位为 720p、480p、360p，不向上放大：480p 原件只生成 480p 和 360p；尺寸足够的原件可加入 720p。以 TS 跑通实际链路，fMP4 的初始化段和结构差异放在同一部分对照讲解，不另开学习单元。

核心知识：m3u8 与分片的关系、分片时长、关键帧对齐、多档共同时间线、TS/fMP4、手动选档和自适应选择。由 FFmpeg HLS muxer 生成产物，讲清 `hls_time`、`hls_segment_type` 等实际用到的选项；分片需要可解码起点，单加标志不能制造关键帧。

服务端提供派生资源登记、基本处理状态、列表及分片的读取授权；原件状态与 HLS 状态分开。上传成功后自动入队，服务端以独立子进程串行转码、分片，再原子公开完整产物；具备基本超时、失败重试和重启恢复。程序在本机 WSL 编译，运行处理在服务器。分布式调度和更多运维能力留到阶段 11。

服务端返回实际已生成、已发布且可播放的档位列表（档位标识、显示名称、实际宽高与播放入口），与 HLS 主列表保持一致。最大可播放清晰度取列表中的最高档，不能只凭源视频高度推断所有低档均已可用；未生成或失败的档位不作为可播放选项返回。前端根据返回列表动态生成选项，不写死 720p/480p/360p。

客户端明确区分 HLS 和 MP4 输入，不能把 m3u8 交给当前强制使用的 mov 解封装器。先实现可用档位间手动切换并保持播放位置；再用小实验或成熟播放器观察吞吐、缓冲与自动选档的关系，不要求本阶段重写完整 Qt ABR 调度器。列表、初始化段与媒体分片都要有授权，下载入口继续保存原始 MP4。

成果与验证：聊天视频可以通过 HLS 播放和切换清晰度；480p 原件不出现 720p 选项，高分辨率原件在 720p 产物就绪后可显示该档；前端选项与实际就绪资源一致；未授权用户不能直接读取分片；能解释关键帧为何影响分片和换档，以及服务端生产多档与客户端选择档位的区别。

知识文档为 `08-媒体处理与HLS点播.md`，也按这两部分组织，具体 API 参数随对应代码讲解。

### 9 直播推流、接入与分发

阶段成果：文件先模拟实时源，之后用 OBS 桌面/麦克风采集作真实源；推到媒体服务后，多个观看端能从当前直播位置加入。聊天系统负责直播资源的业务权限与状态，Qt 负责观看。无需专门学习摄像头设备接入。

先复用一个成熟 C++ 媒体服务建立可观察的基线，优先 SRS；ZLMediaKit 用于后续针对性源码对照，不要求同时部署两套。复用协议实现的同时，必须带读接入、流注册、GOP 缓存、订阅者分发这几条实际调用链，并完成 C++ 业务适配；不能只停在修改配置和启动服务。

1. 文件推流：先用 FFmpeg 命令确定样本和时间线，再用 C++ libavformat 实现最小推流程序。读取编码包、转换时间基、按单调时钟节奏送出，通过 RTMP/FLV 输出；兼容的编码流可转封装推送，无需每个观看者都重新编码。文件模拟源需要节奏控制，真实采集源的数据生产本身有节奏，不能重复盲目限速。
2. 接入与分发：理解 RTMP 握手、chunk 与媒体 message 的关系，FLV tag、音视频 sequence header、H.264 SPS/PPS 与 AAC 配置。服务端维护流标识、发布者及订阅者；中途加入先取得编码配置和可解码起点，观察 GOP 缓存为何影响首帧与延迟。
3. 两种输出：先 HTTP-FLV 连续响应，再直播 HLS 滑动列表。前者与阶段七对固定文件发 Range 不同；后者会持续生成分片、更新列表并清理过期数据。客户端明确区分 FLV/HLS 直播输入，不能沿用强制 mov 的 MP4 分支；界面显示直播状态，初期不把直播当成有固定总时长的点播进度条。
4. 断线与真实源：实现有限退避重连、发布者退出/重入和观众恢复。用 OBS 桌面采集对照文件模拟源；观察时间戳重置、重复 GOP、音频间断及 HLS discontinuity 的含义，不简单拼接两次会话的时间戳。

重点 API/模块：`avformat_alloc_output_context2` 的 FLV 输出、`avio_open2`、写包与中断回调；媒体服务的推流/播放鉴权、发布/取消发布通知、流状态查询。业务授权与音视频数据传输分别观察。

验收：两个观看端中途加入、推流断开后恢复、不同分发方式正常播放；用同一时钟域的标记或画面时钟观察端到端延迟，区分首帧时间与稳态延迟，不预先承诺固定延迟数字。知识文档为 `09-直播推拉流与分发.md`。

### 10 RTP/RTCP：实时媒体的分包、重组与反馈

阶段成果：用已有编码文件和本机 UDP 环境完成 C++ RTP 发送、接收与 RTCP 统计，不依赖摄像头、ONVIF 或 GB28181。RTSP 只在需要时解释为会话控制协议，不把它与 RTP 混成同一种传输。

1. 从抓包与最小 RTP 收发开始：版本、负载类型、序列号、时间戳、SSRC、marker、网络字节序和 MTU。序列号随包推进，时间戳表达媒体采样时刻；同一视频访问单元拆成多包时可以共用时间戳，时间戳不是收包时间也不是统一的毫秒数。
2. 先做 H.264 单 NAL/FU-A 分包和重组，再解释聚合包与 SDP/编码参数。不能把任意 AVPacket 原样装进 UDP 就认为符合 RTP 负载格式。接收端恢复完整访问单元后才送 FFmpeg 解码；对丢失的分片做明确丢弃与恢复策略。
3. 处理乱序、重复、丢包、序列号回绕和有限抖动缓冲；学习等待重排与播放延迟之间的取舍。丢包、乱序、延迟注入先在本机隔离网络做，不直接修改公网服务器全局网络规则。
4. RTCP 学 SR/RR、NTP 与 RTP 时间戳映射、包/字节统计、丢包与抖动；再加入音轨观察跨轨同步。RTP/RTCP 不会自动保证可靠传输，NACK/PLI 等反馈机制需要明确协议扩展和发送端处理，作为这一阶段后半部分逐项实验。

重点 C++ 代码：Boost.Asio UDP socket 与定时器、包头解析、NAL 分包器、按序号维护的有界接收缓冲、RTP 时间戳展开与时钟映射。先借助 FFmpeg 作为互操作对端，再观察一个成熟 C++ 项目中的对应模块，避免只验证自己发送给自己的私有格式。

验收：正常网络可播放；已知注入的乱序/丢包能在抓包和统计中对应；缓冲不无限增长，缺失分片不会当成完整帧解码；能解释同步信息和反馈信息各自的用途。知识文档为 `10-RTP与RTCP.md`。

### 11 并发分发、故障恢复与服务端工程化

将第八、九阶段已有链路作为对象，补足贴近 C++ 服务端开发的资源与生命周期问题。基础限额从接入时就设置，本阶段再做有证据的测量和改进。

| 专题 | 实际代码与实验 |
|---|---|
| 多观看者分发 | 共享不可变编码数据的所有权、每个订阅者的发送队列、异步发送期间的对象存活、断开时取消与释放 |
| 慢客户端与背压 | 按字节/时长设置队列上限；点播可暂停推进，直播不能无限落后，按依赖跳到可解码 GOP 或断开慢订阅者 |
| 任务恢复 | 工作进程退出、超时、重复执行、半成品清理、任务状态与文件发布的一致性；先单机受控恢复，不先造大型调度平台 |
| 观测与排障 | 连接/流/任务标识、首帧、吞吐、缓冲、失败原因、CPU、内存和磁盘；能沿一次真实请求串起业务与媒体日志 |
| HTTP 与缓存 | 私有授权与共享缓存的边界、列表更新与不可变分片、源站/缓存层职责；先在本机代理上理解，不要求购买 CDN |
| 录像与时移 | 先将直播录成可恢复播放的文件，再用有限 HLS 历史窗口理解 DVR；明确保留时长、空间与删除策略 |

验收只做有目的的小规模实验：一个慢观看端不能明显拖住其他观看端；观看端退出后资源释放；工作程序失败不使聊天服务退出；能用数据说明吞吐瓶颈在网络、磁盘、计算还是队列。公网带宽有限，大规模容量实验留在本机。知识文档为 `11-流媒体服务资源与故障处理.md`。

## 贯穿各阶段的构建、部署与资源安排

客户端继续在 Windows 使用已验证的 Qt Kit；服务端及 C++ 媒体程序在本机 WSL 编译 Linux 产物，遵循 `docs/BUILD_DEPLOY_HANDOFF.md`，不在小内存云服务器编译。每次部署核对目标架构、动态库、运行参数和所需数据变更。

Linux 程序在本机 WSL 编译，上传后的转码和分片在服务器后台执行；单任务、逐档处理、有限线程。候选 720p/480p/360p 按源尺寸筛选，不向上放大。测量输出体积、峰值内存和处理速度后，再决定是否增加档位或并发。录像、HLS 分片和临时转码输出都要有明确保留边界。

每次只验证新增链路和相关失败路径。日志、ffprobe、抓包和实际播放各回答不同问题；成功启动进程不等于媒体链路通过。阶段计划不代替实施前对具体接口和线程/进程边界的说明。

## 每次一起学习的方式

1. Codex 先说明当前要解决的问题，用当前样本解释必要概念和数据流。
2. 教学小项目由 Codex 完整编写并做必要验证，再结合数据流和 API 调用关系解释机制；tianmu_sama 通过阅读、提问和观察理解。
3. 实际项目由 Codex 完成外围接入和核心逻辑，讲清函数契约、资源所有权、状态转换及设计理由。理解困难时补充具体数值、示意图或短小示例，不依赖补写代码推进。
4. 共同检查实现和执行结果，关注控制流、资源所有权及错误路径；通过更换样本、暂停、拖动或限速验证理解，发现问题先定位根因。
5. 每阶段在 `D:\chat_server\ChatServer\docs\音视频学习` 建立一份学习文档，开讲前简要写入知识关系、关键概念和 API 名称及作用。阶段文档不放链接，必要知识直接写清。后续提问先在对话中展开，等 tianmu_sama 明确要求总结时，再将问答精炼、去重后补入对应文档，保留 tianmu_sama 自己的笔记。学习进度和协作约定另记在学习记录中。

本音视频与流媒体学习计划的阶段示例及实际项目接入均直接实现，不采用 TDD，不铺开大量测试；这是 tianmu_sama 明确确认的专项约定。验证只覆盖本次目标所必需的编译、代表样本运行与关键输出核对；存在具体风险时再补充必要的异常检查，避免无依据地扩大测试范围或反复回归。例行小改仍遵循不超过 50 个实质行时静态核对的规则，除非明确要求编译或测试。重点投入知识讲解、清楚的代码注释和 API 调用关系。
